# BEAN Folio — Migrations (additive-only policy, as practiced in this repo)

**Summary:** BEAN Folio carries **no `prisma/migrations/` history**. SQLite (dev/sandbox) is
managed with `prisma db push`; PostgreSQL (production target) is managed with reviewed,
additive DDL generated by `prisma migrate diff` and applied by hand after a backup. This doc
is the operational policy: the exact procedure used in this repo, the rollback procedure, the
destructive-migration ban, the backup/restore drill, and the validation checklist.

**Status:** As practiced in this repository. Background and engine-swap details live in
`docs/deployment.md` (§0.4–§0.5, §3.3) and `docs/database.md` (§6); the queue behaves
migration-agnostically (`docs/ops/RUNBOOK-QUEUE.md`).

---

## 1. The two sources of truth (and the parity gate)

| Schema | Engine | Used by | Managed with |
|---|---|---|---|
| `prisma/schema.prisma` | SQLite (`db/custom.db`) | sandbox/dev, `db:push` | `prisma db push` (additive only — the `db:push` script carries no `--accept-data-loss` and must never regain it) |
| `prisma/schema.postgres.prisma` | PostgreSQL | the **Vercel build** (`vercel-build` runs `prisma generate --schema prisma/schema.postgres.prisma`) and any managed-PG deployment | reviewed DDL via `prisma migrate diff` (this doc) |

Both files currently describe the **same 88-model data model** (85 models
after the M22 Phase 2 restoration, plus the three O1 Opportunity Exchange
employer-identity tables — `EmployerOrganization`, `EmployerMembership`,
`EmployerVerification` — added 2026-11-16; the pre-O1 count of 45 stated here
had drifted stale and was corrected in the O1 docs pass). The Vercel build generates its
client from the postgres mirror, so any drift means production references models its client does
not have — the exact failure that once stranded `AgentArtifact` / `SiteStudioSession` /
`SiteStudioMessage` out of the mirror (see `docs/architecture-review/BOTTLENECK_REPORT.md` B-2).

**The parity gate is mandatory for every schema change:**

```bash
bun scripts/check-schema-parity.ts        # exit 1 on drift
```

Run it before committing any change to either schema file. A schema PR that fails parity does
not ship.

## 2. Additive-migration policy (the actual procedure)

Every schema change is **additive by construction**: new tables, new columns with defaults, new
indexes, new foreign keys. Nothing that rewrites or deletes existing data ships in the same
change. The procedure below is what this repo actually does — in order:

### Step 0 — Take a backup first (non-negotiable)

```bash
# SQLite (sandbox / single-node deployments):
bun scripts/backup-db.ts                    # → db/backups/beanfolio-YYYYMMDD-HHMMSS.db + .json manifest
# PostgreSQL:
pg_dump --no-owner --no-privileges --format=custom \
  --file="pre-migration-$(date -u +%Y%m%d-%H%M%S).dump" "$DATABASE_URL"
```

The backup is the rollback plan. If you cannot take one, you cannot run the migration.

### Step 1 — Edit BOTH schemas in the same change

Add the model/column/index to `prisma/schema.prisma` **and** `prisma/schema.postgres.prisma`
identically. Keep the model bodies byte-equal modulo provider-specific attributes (there should
be none in Phase A — the mirror is deliberately provider-switch-only; see the header of
`prisma/schema.postgres.prisma`).

### Step 2 — Parity gate

```bash
bun scripts/check-schema-parity.ts          # must exit 0
```

### Step 3 — Push SQLite (dev/sandbox)

```bash
bun run db:push                             # prisma db push — NO --accept-data-loss, ever
```

If `db push` proposes data loss, STOP: your change is not additive. Redesign it (§4).

### Step 4 — Generate the PostgreSQL DDL and REVIEW it

Two cases:

- **Fresh/empty production database** — generate the full from-empty DDL from the *current*
  schema and review it before applying:

  ```bash
  bunx prisma migrate diff --from-empty \
    --to-schema-datamodel prisma/schema.postgres.prisma --script > pg-migration/NN_initial.sql
  ```

  ⚠️ The checked-in `docs/deployment/initial-schema.sql` / `additive-schema.sql` are **HISTORICAL
  pre-LAXII artifacts** — never apply them to a database meant for the current app.

- **Existing production database** — generate the additive delta against the live database (or a
  snapshot of it) and review every statement:

  ```bash
  bunx prisma migrate diff \
    --from-url "$DATABASE_URL" \
    --to-schema-datamodel prisma/schema.postgres.prisma --script > pg-migration/NN_additive.sql
  ```

  The repo's read-only probe does the same inventory check without DDL and prints an
  additive-only plan for exactly the objects the database lacks:
  `bun scripts/check-postgres-schema-readiness.ts` (exit 0 = ready · 1 = prints plan · never executes).

**Review rule:** the generated SQL may contain only `CREATE TABLE / CREATE INDEX / CREATE TYPE /
ALTER TABLE … ADD COLUMN / ADD CONSTRAINT`. **Any `DROP`, `ALTER … ALTER COLUMN`, `RENAME`,
`TRUNCATE`, `DELETE`, or `UPDATE` statement = destructive → §4 approval flow, not this flow.**

### Step 5 — Apply to PostgreSQL (manual, explicit, once)

`psql "$DATABASE_URL" -f pg-migration/NN_additive.sql`, or paste into the provider SQL editor
(e.g. Supabase → SQL Editor). Most generated DDL from `migrate diff` carries
`IF NOT EXISTS`-style guards only partially — **apply exactly once**; if a statement fails,
re-run the readiness probe and apply only the statements for objects still missing.

### Step 6 — Verify

```bash
bun scripts/check-postgres-schema-readiness.ts   # exit 0
bun scripts/verify-postgres-migration.ts         # row counts / FK orphans / dedup invariants (PG)
```

Then application-level checks: `GET /api/ready` → 200, `GET /api/professions` (DB-backed),
register a throwaway account, exercise one upload. Registration is transaction-safe — on a
database missing new columns the whole write rolls back with a 500 rather than leaving a
half-created account.

### Why `migrate diff` and not `prisma migrate dev`?

There is no migrations history to replay; the deployment model is "client generated from schema,
DDL applied deliberately." `migrate diff --from-empty/--from-url --to-schema-datamodel` produces
exactly the reviewed SQL needed without inventing a shadow history. If the project ever adopts
`prisma/migrations/`, that is its own migration (baseline the current schema first) — out of
scope here.

## 3. Rollback procedure

Rollbacks are **forward-only** at the schema level; data-level rollback means restore.

| Situation | Action |
|---|---|
| App bug after a migration, schema is additive | **Do nothing to the schema.** Roll the app back (previous build artifact — `docs/deployment.md` §3.8); additive columns/tables are harmless to app N-1 by construction (expand → deploy → contract). |
| Migration half-applied (some statements failed) | Re-run the readiness probe, apply only the missing objects. Additive DDL applied twice fails loudly on `ADD COLUMN` (duplicate) — never force it; probe first. |
| Migration applied, data corrupted by the change | Restore from the Step-0 backup (`scripts/restore-db.ts <backup> --force` on SQLite; `pg_restore` on Postgres), then re-apply a corrected migration. Document what was lost (rows written between backup and incident). |
| Production cutover rollback (SQLite→PG) | The prepared runbook is `pg-migration/rollback.md` (engine-behavior matrix + cutover steps). |

**Never** write a "down migration" by hand to reverse a data change — restoring a backup is the
only data-accurate path.

## 4. Destructive-migration ban + approval requirements

Destructive changes are **banned by default** and require explicit human approval at release
level, not just code review. Destructive means any of:

- `DROP TABLE`, `DROP COLUMN`, `DROP INDEX`, `DROP CONSTRAINT`
- `ALTER COLUMN` type changes (e.g. `text` → `integer`), including Prisma `@db` attribute flips
- `RENAME` of tables/columns (do add-new + backfill + read-both + remove-old in *separate*
  approved releases instead)
- Tightening uniqueness/not-null on existing data
- Any statement that deletes or rewrites rows (`DELETE`, `UPDATE … SET` over existing rows,
  `TRUNCATE`)
- Switching the engine's native types in Phase B (`jsonb`, `text[]`, enums) — that is a
  deliberate, separately-approved PR per `docs/database.md` §6

Approval checklist (all boxes before execution):

1. Written justification: why the data loss / rewrite is necessary and what is lost.
2. Backup taken **and restore-verified** (§5 drill) within the last 24h.
3. Two-person review of the exact SQL (no "trust the generator" for destructive statements).
4. Maintenance window scheduled; app stopped; queue workers stopped (`QUEUE_ENABLED=false` or
   SIGTERM the drain workers).
5. Post-change verification plan prepared (§2 Step 6) and a rollback owner named.

## 5. Backup / restore drill (using the committed tooling)

Scripts (no Next.js imports, safe to run while the app is down or up; backup is read-only on the
source):

```bash
bun scripts/backup-db.ts [--out <dir>] [--keep <N>]     # VACUUM INTO → db/backups/, keeps 14
bun scripts/restore-db.ts <backupFile> [--force] [--target <path>]
```

`backup-db.ts` prints one JSON manifest line (`file`, `bytes`, `sha256`, `tables`, `method`) and
writes a `.json` sidecar the restore script verifies. On a PostgreSQL `DATABASE_URL` it prints
the exact `pg_dump` command and exits 0 without side effects (no JS pg_dump — by design).

**Drill (quarterly, and after every destructive-adjacent change):**

1. `bun scripts/backup-db.ts --out /tmp/drill` — record the printed `sha256`.
2. Restore into a **throwaway path** (never over the live DB):
   `bun scripts/restore-db.ts /tmp/drill/beanfolio-<stamp>.db --target /tmp/drill/restored.db`
   — the script verifies the sidecar sha256, pre-flights `PRAGMA integrity_check` on the backup,
   and re-verifies the restored file; expect `restore.ok … "integrity":"ok"`.
3. Boot the app against the restored copy:
   `DATABASE_URL="file:/tmp/drill/restored.db" NODE_ENV=production bun .next/standalone/server.js`
4. Verify `GET /api/health`, `GET /api/ready`, one login, one project read, one queue tick.
5. Record measured RTO (restore + boot + verify time) and RPO (age of the backup used) in the
   ops log. A backup that has never been restored is a hypothesis, not a backup.

Postgres drill: `pg_restore --clean --if-exists --dbname "<scratch-db>" <dump>` into a scratch
database, point a throwaway app instance at it, same verification list. Managed-provider PITR
must be exercised through the provider's restore-to-timestamp flow at least once before relying
on it.

## 6. Migration validation checklist

- [ ] `bun scripts/check-schema-parity.ts` → exit 0 (both schemas edited, identical models)
- [ ] Change is purely additive (new tables / columns-with-defaults / indexes / FKs)
- [ ] `bun run db:push` (SQLite) succeeds with **no data-loss proposal**
- [ ] Backup taken *before* touching any shared/production database (`backup-db.ts` / `pg_dump`)
- [ ] PG DDL generated with `prisma migrate diff` and **eyeballed statement by statement** —
      zero `DROP`/`ALTER COLUMN`/`RENAME`/data-touching statements
- [ ] `bun scripts/check-postgres-schema-readiness.ts` → exit 0 after applying
- [ ] `bun scripts/verify-postgres-migration.ts` → counts/orphans/invariants pass (PG)
- [ ] App-level: `/api/ready` 200 · `/api/professions` 200 · throwaway register/login ·
      one upload · queue tick healthy (`/api/health` → `queue.byStatus` populated)
- [ ] Previous app build still boots against the new schema (N-1 compatibility)
- [ ] If Phase-B native-type change: separate PR, app-code changes included, approval per §4
