## 1. Product outcome

Make LAXII capable of producing professional, user-directed visual assets across common creative formats while preserving truth, identity, text accuracy, privacy and export integrity.

The user should be able to describe the goal naturally, upload permitted reference material, choose or confirm a canvas, review the composition, request revisions, approve the result, and export a real file at the promised dimensions.

M33.4 has three separately testable workstreams:

1. **M33.4-A — Universal Banner Canvas Registry:** replace the one-preset limitation with a versioned set of verified canvas presets plus bounded custom sizes.
2. **M33.4-B — Brand/Audience Typography:** extend the existing deterministic renderer to use real, licence-reviewed font files, script coverage, measured line layout and brand/audience-aware recommendations.
3. **M33.4-C — Identity-Lock Avatar / Background Replacement:** design and implement a new, strict pixel-preserving workflow. This is a new implementation, not restoration of an engine that still exists.

Do not fold M33.5 resume/cover-letter/ATS work or M35 RIISHE tool orchestration into this milestone. Keep their existing routes and behaviour untouched.

## 2. M33.4-A — Universal banner canvas registry

### 2.1 Required canvas families

Design the registry to support at least these families. They are categories, not permission to invent platform dimensions:

- BEAN Folio profile/portfolio cover and published-site hero.
- Professional profile/header banners.
- Social network page/profile covers and feed creatives.
- Square and portrait social posts.
- Vertical stories and short-form video covers/thumbnails.
- YouTube/channel and video thumbnail assets.
- Website hero, landing-page campaign and product-feature banners.
- Product launch, sale, event, webinar, course and announcement graphics.
- Advertising variants and display creatives.
- Presentation/title slides and editorial/print canvases where supported by actual export requirements.
- User-defined custom dimensions.

The first implementation must cover the most-used high-value presets, not pretend to implement every platform's entire advertising specification catalogue. Expand the registry additively after each platform specification is verified.

### 2.2 Platform dimension evidence

For every platform-specific preset:

- Check the platform's current first-party help/business documentation at implementation time.
- Record the official source URL, source title, checked date, exact pixel dimensions, aspect ratio, file-size cap if documented, and any central/mobile/desktop safe-area rule.
- If the official source does not specify a value or the documentation is ambiguous, label the preset as a recommended generic canvas rather than an official platform preset.
- Do not take dimensions from blogs, AI responses, search snippets or old screenshots when first-party documentation is available.
- Keep platform dimensions and safe-area definitions versioned so a later platform change does not silently mutate an existing project.

The current `src/app/api/laxii/banner-presets/route.ts` comment mentions examples such as YouTube dimensions, but the live registry currently has one actual preset. Update stale comments once the real registry is implemented; comments must describe the current behaviour.

### 2.3 Registry contract

Create a typed, schema-validated, versioned canvas contract. Adapt names to existing conventions after source inspection; do not duplicate an existing type if one already fits.

Each canvas definition should contain:

- Stable `id`/`slug` and explicit `version`.
- Human label, purpose, target platform (optional), and category.
- Exact integer width and height in pixels.
- Derived aspect ratio; never store inconsistent duplicate ratio values.
- One or more named safe areas as pixel rectangles, with device/context labels (e.g. mobile crop, desktop crop, central safe area).
- Composition guidance, recommended subject zones and text zones.
- Minimum and maximum content bounds.
- Supported export formats and transparent/opaque-background capability.
- Documentation URL, checked timestamp and source-verification status for any platform claim.
- Compatibility metadata indicating whether an existing saved project can migrate safely.

Safe-area rectangles must validate as positive, in-bounds coordinates. Never allow negative coordinates, zero sizes or a rectangle extending outside the canvas.

### 2.4 Custom canvas sizes

Allow a user to set a custom width and height with strict validation. The agent must inspect the existing upload/export limits and available memory before setting caps. Establish explicit maximum width, height, total pixels and encoded output size; test the caps. Reject out-of-range requests with a useful error rather than clipping, stretching or allocating unbounded buffers.

Never silently change custom dimensions. Show the final dimensions and aspect ratio before generation/export. If the provider cannot render the exact dimensions, generate at a supported size, then use a documented deterministic crop/outpaint/composite plan. Report any crop and get approval where it changes subject content.

### 2.5 Backward compatibility — mandatory

- Keep `BANNER_WIDTH = 2048`, `BANNER_HEIGHT = 687`, `BANNER_PRESET_SLUG = "bean-folio-banner"` and `BANNER_ASPECT_RATIO` compatible unless the existing source proves a safe additive migration is required.
- Existing profile covers, published-site hero strips, stored versions, exports and tests must continue to work exactly as before.
- Keep legacy `presetSlug` requests valid.
- Do not force existing users into a new canvas or crop.
- Add an explicit migration/normalization map only if needed; test round-trip loading of old saved objects.
- Verify that public profile/banner rendering continues to display the legacy 2048×687 asset correctly.

### 2.6 UI/UX

Extend the existing `LaxiiBannerPanel` rather than replacing the LAXII experience:

- Searchable, grouped preset picker with plain-language purpose and dimensions.
- Custom-size entry with live ratio preview and validation.
- Toggleable safe-area and crop guides, clearly distinguished from the final artwork.
- Subject focal-position guide and editable text-safe placement guidance.
- Responsive preview that represents the actual canvas ratio; do not confuse the editor viewport with export pixels.
- Export confirmation with exact dimensions, format, transparency and file-size information where measured.
- Preserve the existing export approval gate and version ownership semantics.

No decorative dead controls. Every control must change the rendered state or perform its advertised operation.

## 3. M33.4-B — Brand/audience-aware deterministic typography

### 3.1 Extend, do not replace

The existing `src/lib/laxii/typography.ts` already renders text as a deterministic layer and measures rendered ink. Preserve its important guarantees:

- The image model must not paint required wording, logos or critical labels.
- Exact user strings are rendered by the deterministic text engine.
- The renderer measures actual output and checks safe areas and contrast.
- Any font fallback or missing glyph must be reported, not hidden.
- Preserve current DejaVu fallback behaviour for legacy requests.

Current limitation: `typography.ts` maps its three semantic font choices to DejaVu Sans/Serif/Mono. It does not yet resolve all 129 `SITE_FONTS` families to actual server-available font files.

### 3.2 Font resolution contract

Create an explicit LAXII server-renderable font registry or a safe adapter over the current `SITE_FONTS` metadata. It must distinguish:

- A font known to the GIFTZ website registry.
- A font file actually available to LAXII's server-side renderer.
- A font whose licence and redistribution rights have been reviewed.
- A font with the required weight/style and glyph coverage for this exact text.

A registry entry should record family, source, version, file path/package, supported weights/styles, script/language coverage, licence identifier, attribution/notice requirements, and a content hash. Only `verified + available + glyph-covered` entries can be used for server rendering.

Do not download fonts from a CDN at export time. The renderer must be deterministic and capable of running without an external font network request. Use self-hosted/bundled assets for approved fonts. Keep font asset sizes controlled and lazy-load only what the selected job needs.

### 3.3 Font recommendations — use creative context, not psychological profiling

The user's phrase “fonts based on psychology” should be implemented as **brand-, audience- and brief-aware visual tone recommendations**, not psychological diagnosis or hidden profiling.

Permitted recommendation inputs:

- User-selected brand adjectives (e.g. premium, friendly, technical, editorial, playful, formal, calm, energetic).
- Explicit target audience and creative purpose.
- Industry/profession when the user supplies it or it is in their own authorised profile context.
- User-selected design language, palette and logo/brand kit.
- Readability constraints, language/script, device/format and exact content length.

Never infer or store sensitive personal traits, mental health, personality diagnoses, ethnicity, religion, political views or other protected characteristics. Do not state that a font scientifically changes a person's psychology. Recommendations must be framed as design conventions and explainable choices, not scientific certainty.

Each recommendation should give:

- Display/headline family and body/supporting family.
- Available weight and style for each actual font file.
- The intended tone and why the pairing matches the stated brief/audience.
- Readability and script-coverage confidence.
- Licence state and any limitations.
- A live specimen preview using the user's exact text.

Allow user override, save a brand kit, create variants, undo and compare. The explicit user choice always wins.

### 3.4 Layout and rendering requirements

- Preserve exact spelling, punctuation, case and Unicode code points from user-provided strings.
- Measure text using the actual chosen font files and target render engine.
- Handle line breaks, line-height, kerning, tracking, word spacing, alignment, weight, glyph fallback, long words and text overflow.
- Support script-aware shaping for Tamil, Hindi/Devanagari, Bengali, Telugu, Malayalam, Kannada, Arabic and other scripts actually supported by the selected fonts. Do not assume a font has full glyph coverage because it renders Latin characters.
- Add tests for combining marks, ligatures, right-to-left runs, mixed-script text and emoji fallback where those are supported. If the render stack cannot shape a script correctly, report that script as unsupported for that font and choose a verified fallback or ask the user to approve a different treatment.
- Render logos as original image/vector assets, not retyped approximations.
- Verify all actual text pixels remain inside canvas and safe areas, and verify contrast against the rendered background.
- Keep the existing measured-ink and `verifyInkApplied` checks; extend them rather than bypassing them.

### 3.5 Font licensing and provenance

- Check each individual font's licence. A registry or aggregator's code licence does not automatically license the font files it distributes.
- Preserve required OFL/Apache/UFL notices and copyright metadata when bundling or distributing font software.
- Do not bundle proprietary OS fonts merely because they are installed on a developer machine.
- Update the third-party notices/licence register for any new font binaries or packages.
- No font is production-eligible until the exact family, package/file version, licence and glyph coverage are verified.

## 4. M33.4-C — New identity-lock avatar and background replacement

### 4.1 Correct product promise

Create two visibly distinct modes:

**Identity Lock — background-only composition**

- The original user-supplied subject is preserved as source pixels.
- The system creates/replaces the background separately, then composites the original foreground over it.
- The face core must remain pixel-identical to the source input.
- The system must not regenerate, beautify, reshape, relight, recolour, smooth, sharpen, stylise or otherwise edit protected face pixels.
- The mode is not an outfit-changing, expression-changing or face-restyling generator.
- If the mask cannot be trusted, the operation stops and asks for correction. It must never silently fall back to a generative portrait and call that identity-preserving.

**Creative Restyle — best-effort likeness**

- Existing avatar presets/providers may continue to create a re-rendered subject.
- Label the mode “AI-restyled / likeness may vary” or equivalent.
- Do not promise exact identity or pixel preservation.
- Never silently convert an Identity Lock request into Creative Restyle.

### 4.2 Strict pixel-preservation definition

A claim such as “face unchanged” must be backed by a testable rule.

- Preserve the original source image bytes separately and never overwrite them.
- Create a user-reviewable foreground matte and a separate protected-face core region.
- The protected-face core is copied from the original source image without pixel transforms. After final decode, every protected core RGB/RGBA pixel must be byte-identical to the corresponding source pixel, accounting only for a documented coordinate transform if the user explicitly approved a crop before processing.
- Do not apply colour grading, sharpening, denoising, tone mapping, resize interpolation or JPEG recompression to the protected-face core.
- Use lossless output for the strict verification path (PNG or lossless WebP). If JPEG is offered as a convenience export, clearly state that lossy encoding cannot maintain byte-identical pixels; the verified master remains lossless.
- Edge feathering may affect boundary pixels. The core face region must remain fully opaque and excluded from blending. Report the protected region and edge-treatment rule.
- For a wider “whole-subject preserved” claim, test the entire fully opaque foreground region. Do not equate a partial-alpha hair/edge pixel with an unchanged pixel.
- Store a mask/version record and deterministic verification report with the generated asset.

A pixel-identical face core does not prove the segmentation is semantically correct. Mask accuracy still needs user review and quality checks.

### 4.3 Processing architecture

Implement as a new, isolated pipeline using existing storage, ownership checks and job lifecycle where appropriate:

1. Validate source media format, decoded dimensions, colour profile/orientation, file size and ownership.
2. Preserve immutable original bytes and compute a cryptographic hash.
3. Generate an assistive foreground matte locally or through an explicitly approved local worker. Do not send the original portrait to a remote generation provider for Identity Lock mode.
4. Generate the new background from the user's text brief without using the face/portrait as a generation reference.
5. Present the foreground mask and proposed composition for user review. Allow zoom, protect brush, erase brush, edge refine and reset.
6. Create a protected-face core mask. A detector may propose a region but must not perform face recognition, identity matching or identity inference. User confirmation/editing is required before finalisation.
7. Composite the unchanged source face/foreground pixels over the generated background. All geometry changes must be explicit and previewed. No non-uniform stretching.
8. Verify protected-region pixel identity, mask bounds, no clipping, dimensions, decodability and alpha-edge constraints.
9. Show before/after, overlay, mask view and verification status.
10. Require explicit user approval before saving as the active avatar or publishing it to a profile.
11. Keep the original version, allow undo/restore, and apply owner-scoped retention/deletion rules.

### 4.4 Safe degradation and failure behaviour

- Poor hair/edge segmentation, occlusion, low resolution, multiple people, face at border, unusual pose, transparent source or uncertain masks must trigger warnings or manual correction.
- If the protected face core is cut by the mask, the job fails closed.
- Do not invent a successful verification score. Report measured pixel equality count, protected area and failed checks.
- Provide an explicit “keep original background” or “cancel” path.
- If local inference is unavailable, report that the strict mode cannot run in the current environment; never transparently call a paid/remote model.
- Keep existing provider constraints and rate/cost guards. No new paid services, keys or cloud provisioning without owner approval.
- No hidden GPU/CPU selector in the UI. Detect capability internally; choose a verified lightweight path automatically. Make resource usage and download requirements visible where material, but do not expose low-level model selection as a user-facing setting.

### 4.6 Model provenance checklist

Before any model/weight is accepted:

- Exact upstream repository and immutable commit/revision.
- Exact model card and licence metadata at that revision.
- Weight file SHA-256 and size, checked against the upstream artifact.
- Associated processor/config and intended image-size/normalisation requirements.
- Training dataset and any usage restrictions disclosed by upstream.
- Full dependency licence tree and security scan.
- Measured CPU/GPU/RAM/VRAM and cold/warm inference time.
- Benchmark outputs from the same representative fixture set.
- Documented fallback and deletion/cache policy.

If any provenance or commercial-use question is unresolved, do not ship that model. Record it as `not-approved` or `owner-review-required` rather than guessing.

## 5. Creative direction and “FilmCraft” treatment

Where a user requests cinematic or FilmCraft-like creative direction, translate that into controllable design attributes rather than copying a proprietary design or assuming a hidden feature exists:

- Framing, subject scale, visual hierarchy and negative space.
- Lens/perspective language only as a visual prompt aid, not a claim about real camera capture.
- Lighting direction, softness, contrast and background depth.
- Palette/colour grade, atmosphere, texture and restrained grain.
- Banner-safe text zones, logo placement and legibility.
- Exact brief strings rendered by deterministic typography.

The user remains in control of the selected mood. Do not add a new “FilmCraft” feature or dependency unless the repository contains an actual specification for it; inspect and report any matching in-repo reference before interpreting the phrase as a named integration.

## 6. Shared quality, storage and security contracts

- Reuse LAXII's existing brief, job, version, storage, ownership, approval, validation and measured quality mechanisms.
- All source media and generated outputs remain user-owned and owner-scoped. Do not make private references public as part of generation.
- Do not include original portrait data, prompts or sensitive user media in general logs. Prefer metrics-only event data, with redaction and bounded retention.
- Limit input dimensions, decoded pixels, file size, frame count and concurrent jobs to prevent decompression bombs and resource exhaustion.
- Validate actual image content by decoding with the approved image library; do not trust filename extensions or client metadata.
- Check MIME type, allowed formats, path traversal, temporary workspace permissions and cleanup on success, failure, cancellation and timeout.
- No arbitrary remote URL fetches from user-supplied image links unless the existing safe-fetch policy is explicitly followed; prevent SSRF.
- Keep CSRF/auth/owner scope/rate-limit checks on every API path. A user must not be able to request another user's media IDs, job IDs, version IDs or exports.
- Use explicit user approval before an avatar/banner becomes a public profile asset.
- Keep all M33.3 GIFTZ static quality-gate checks unchanged. LAXII image quality checks and GIFTZ website quality checks are separate capabilities.

## 7. Low-spec runtime requirements

Do not make a dedicated GPU mandatory. The feature should select the best verified available execution path internally:

- Use a lightweight ONNX/Transformers.js path where it meets the quality threshold and is compatible with the current runtime.
- Permit CPU execution for supported resolutions, with bounded memory and cancellation.
- Use GPU acceleration when available, without requiring users to choose CPU vs GPU in the UI.
- Load models lazily and cache verified model artefacts. Do not download large model files unexpectedly during a user's generation request.
- Set a model-download consent/notice and show size only when the download is actually needed.
- If the device/server cannot run strict Identity Lock safely, explain the limitation and leave the source unchanged.
- Keep the existing managed image provider behaviour unchanged for regular LAXII generations. Identity Lock must not leak the portrait to the managed provider.
- Do not introduce Ollama or make a new hosted AI provider mandatory.

Benchmark at minimum: CPU-only, integrated-GPU or WebGPU if actually supported, and the repository's available GPU worker. Report cold-start model load, warm inference, peak RAM/VRAM, output resolution and failure rate. No generic “works on low-spec” claim without recorded measurements.

## 8. Test and acceptance matrix

### 8.1 M33.4-A banners

- Existing 2048×687 preset remains byte-for-byte contract-compatible at the API/schema level.
- Preset registry entries are unique, versioned and schema-valid.
- All safe areas remain inside their canvas.
- Every platform-labelled preset has a current first-party source URL and checked date.
- Custom dimensions at lower/upper valid bounds pass; zero, negative, excessive and overflow dimensions fail safely.
- Export decoder reports the exact requested dimensions and expected format.
- Resize/crop planning never stretches an image; focal subject and text remain in the approved safe area.
- Legacy projects load and export without migration loss.
- Existing profile banners, published site heroes and public profile layouts render without regression.
- Browser screenshots at mobile, tablet and desktop widths prove the editor itself has no overflow or broken controls.

### 8.2 M33.4-B typography

- Existing three fallback families and old brief schema remain compatible.
- Every selectable font resolves to a real file with verified weight, licence and glyph coverage.
- Missing file/weight/glyph triggers a specific warning and safe fallback.
- Exact text strings survive rendering, including punctuation and Unicode.
- Test long words, long titles, narrow canvases, multiple lines, RTL, combining marks, Tamil/Indic sample text and fallback boundaries.
- Rendered ink is measured from actual pixels; no off-canvas or unsafe text.
- Contrast measurement is against the final underlying pixels, not just the requested hex value.
- No font network request is required during server export.
- Output is reproducible for the same code, font files, brief and render environment; document any nondeterminism.

### 8.3 M33.4-C identity lock

Create a dedicated synthetic fixture suite with a licensed/owned test image set and deterministic synthetic images. Include single-person portraits, hair detail, glasses, varied lighting/skin/background contrast, non-frontal pose, multiple people, face-at-edge, low resolution, transparent input and intentionally difficult masks.

Required deterministic tests:

- Source bytes remain unchanged in storage.
- Source hash is stable before/after.
- Protected face-core pixels are exactly equal in the lossless final master.
- Every full-opacity preserved subject pixel is copied from the source at the same approved coordinates.
- No non-uniform scaling or unintended geometry transform.
- Invalid/empty/out-of-bounds mask fails closed.
- Poor confidence or ambiguous multiple-subject mask requests manual review.
- Lossy export cannot be labelled pixel-identical.
- Job cancellation/timeout cleans temporary files and does not publish a partial result.
- Non-owner cannot inspect, modify, export or approve another user's assets.
- Background generation request contains no original face/portrait bytes or remotely retrievable source URL.
- No fallback to Creative Restyle on any Identity Lock failure.

### 8.4 Common project checks

Run and report exact results for:

- Focused M33.4 unit/integration tests.
- Full existing test suite, classifying reproduced baseline failures rather than suppressing or weakening tests.
- `tsc --noEmit`.
- Lint (distinguish existing warnings from new findings).
- Prisma/schema parity and Prisma validation if schema files are touched.
- Production build.
- Security/dependency/license scan.
- Existing LAXII API auth/ownership/rate-limit tests.
- Existing GIFTZ project, publishing and M33.3 quality-gate tests.
- Browser tests/screenshots at 390, 768, 1024 and 1440 CSS px where relevant.

Do not state “all tests pass” when the full suite has known failures. Report the exact command, total pass/fail/skip count, baseline comparison and any unresolved result.

## 9. Implementation sequencing and commit boundaries

Implement sequentially so regressions can be isolated:

### M33.4-A — registry and banner compatibility

Deliver typed/versioned presets, official-source evidence, custom canvas validation, UI picker/guides, exact exports and legacy regression tests. Do not start font or avatar changes until this sub-milestone is stable.

### M33.4-B — typeface resolution and composition

Deliver verified font assets/resolution, brand/audience recommendation logic, glyph coverage, rendering measurements, font notices and tests. Do not claim all 129 GIFTZ fonts are server-ready unless every font has actual binary/provenance coverage.

### M33.4-C — Identity Lock proof and production gate

First verify the existing MODNet weights and benchmark a working inference proof. Then implement the protected-core compositing prototype with a reviewable mask and pixel-diff report. Only promote to the production UI after the full test and quality gate passes. If inference or exact pixel preservation cannot be proven, keep it behind a clearly labelled internal feature gate and report the blocker; do not ship a misleading “identity-preserving” switch.

Each sub-milestone must have its own focused tests, evidence, commit(s), and report. No unrelated refactor or feature creep.

## 13. Research references and licence notes

The following public sources were checked while preparing this handoff. They are candidate references, not blanket endorsement of integrating every repository.

### Canvas/editor architecture

- [Konva](https://github.com/konvajs/konva) — MIT 2D scene-graph canvas framework for interactive graphics, transformations, animation and export. Consider only if the existing LAXII panel cannot meet measured canvas-editing requirements without it.
- [React Konva](https://github.com/konvajs/react-konva) — MIT React integration for Konva. It is a canvas primitive, not a complete Canva-like product. Check exact React peer compatibility before adding it.
- [Puck](https://github.com/puckeditor/puck) — MIT React visual page editor. It is more relevant to GIFTZ page editing than LAXII banner rendering, and is not a replacement for the current GrapesJS integration.
- [DesignHub](https://github.com/yakew7/DesignHub) — MIT local-first brand/design toolkit; useful for reviewing brand-kit workflows and asset concepts, not for copying UI wholesale.

### Portrait segmentation / matting

- [Xenova/modnet model card](https://huggingface.co/Xenova/modnet) — declares Apache-2.0 and shows Transformers.js inference. Verify the checked-in ONNX binary hash against a pinned upstream revision before runtime use.
- [SAM 2 official repository](https://github.com/facebookresearch/sam2) — official README states code, demo, training code and checkpoints are Apache-2.0; installation requirements indicate a comparatively heavy PyTorch path.
- [rembg](https://github.com/danielgatis/rembg) — MIT package with multiple model options; upstream explicitly notes model weights have separate licences, and BRIA RMBG-2.0 requires a paid commercial agreement.
- [BiRefNet](https://github.com/ZhengPeng7/BiRefNet) — source repository MIT; independently verify model weights, datasets, memory and commercial-use terms before consideration.

### Typography

- [Fontsource](https://github.com/fontsource/fontsource) — self-hostable font package ecosystem. Its README states that licences vary by individual font (commonly OFL-1.1, Apache-2.0 or UFL-1.0); inspect the selected font package's own licence.
- [Fontsource font files and submission guidance](https://github.com/fontsource/font-files/blob/main/CONTRIBUTING.md) — documents accepted font licence classes and source expectations.
- [Official SIL Open Font License](https://openfontlicense.org/) — authoritative OFL 1.1 text and FAQ.
- [Using OFL fonts](https://openfontlicense.org/how-to-use-ofl-fonts) — explains bundling, embedding, webfont use and preservation of licence information.

### Other creative/resume references for later milestones

- [Reactive Resume](https://github.com/reactive-resume/reactive-resume) — MIT open-source resume builder; later reference for resume workflows, not an M33.4 dependency.
- [CVTailor](https://github.com/Kiranism/cvtailor) — MIT resume tailoring reference; inspect provider/API assumptions and privacy before any later adaptation.
- Do not pull M33.5 resume functionality into M33.4.

**Licence rule:** verify the exact repository commit, package version, transitive dependencies, model card, individual model-weight licence and any dataset restrictions at the time of implementation. Record provenance and notices. Code licence and model-weight licence are different questions.
