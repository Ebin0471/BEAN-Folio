### 1.2 Current limitations to address

1. File extraction returns raw text; it does not create a structured, confidence-labelled facts proposal for user review.
2. The parser currently has no OCR path for image-only/scanned PDFs.
3. There is no dedicated deterministic ATS-readability report or transparent job-requirement evidence map. The word “ATS” in a resume format is a layout/guidance choice, not proof of compatibility with every ATS.
4. There is no first-class Cover Letter document schema, route family, editor, saved library or export flow in the LAXII resume surface.
5. Tailoring updates the existing `LaxiiResume` row. A user should be able to preserve a master resume and create a new job-specific copy without losing the earlier version.
6. PDF/DOCX export validates that a non-trivial file was produced, but M33.5 should add decode/re-extraction round-trip diagnostics and regression fixtures without implying that a third-party ATS was emulated.
7. RIISHE has a general registered tool architecture, but career-document actions must not be wired to unregistered or direct model-executed code. RIISHE orchestration is a later integration gate unless all needed tool permissions and action contracts can be added and tested safely within this milestone.

## 3. Product outcome

M33.5 delivers a reliable, private career-document workflow:

**Import → Review facts → Build master resume → Analyze readability → Compare to a job → Create a tailored copy → Write a truthful cover letter → Review → Save version → Export.**

The product should support:

- Students, fresh graduates, career changers, employed professionals, freelancers, executives, academics, researchers, healthcare and licensed professionals, creatives, media workers, trades and other professions represented by the live taxonomy.
- Different document conventions: short resume, detailed CV, academic CV, research dossier, executive resume, technical resume, journalism/media CV, portfolio CV, international CV and role-specific variants.
- Regional conventions selected by the user (e.g. India, US, UK/EU, Canada, Australia, international), while never asking for or adding sensitive personal details by default.
- Multiple job applications and tailored document copies while maintaining a protected master resume.
- Honest guidance and export diagnostics rather than unsupported claims about hiring systems.

### User-visible product language

Prefer:
- “ATS readability checks”
- “Job-description match analysis”
- “Requirements supported by your resume”
- “Possible missing evidence — confirm before adding”
- “Text extraction quality”
- “PDF/DOCX export verification”

Avoid:
- “Guaranteed ATS pass”
- “100% ATS score”
- “Guaranteed shortlist”
- “Your resume will beat the ATS”
- “AI verified your experience”

## 4. M33.5-A — Source import, extraction and verified fact review

### 4.1 Preserve and improve the current parsers

- Continue supporting the currently implemented PDF, DOCX, TXT and MD inputs.
- Retain the current 10 MB upload cap unless real device/runtime benchmarks justify a different documented limit.
- Keep the parser privacy contract: the parse endpoint returns extracted content and persists nothing by itself.
- Extend beyond the existing 8,000-character ceiling only after tests establish memory/time safety and the existing generation prompt budget can accept the larger input. Report truncation explicitly.
- Validate actual file bytes/signature as well as extension and MIME claim. Reject mismatches and unsupported formats with precise messages.
- Apply bounded file/page/character limits, decompression limits for DOCX ZIP containers, safe XML parsing and timeouts. Do not extract external entities or remote resources.
- Never execute embedded macros, scripts, active PDF content, external links or document attachments.
- Treat uploaded document contents as untrusted data. Prompt-injection text in a resume or job description must remain source content, never become system instructions.
- Do not log full extracted text, email addresses, phone numbers, personal addresses or document bodies. Log only redacted diagnostics and counts.

### 4.2 Structured extraction proposal

Add a typed extraction result (schema versioned) that maps source evidence to the existing `ResumeFacts` shape. Do not alter the established `ResumeData` storage format unless backward compatibility is proven.

Each proposed field/entry should include:
- parsed value;
- source snippet or page/paragraph reference (bounded and private);
- extraction method (`pdf-text`, `docx-text`, `plain-text`, `ocr` when available, or user-entered);
- confidence bucket (`high`, `review`, `low`) with a deterministic basis;
- warnings/ambiguities;
- field provenance (`source-document`, `user-confirmed`, never “verified by AI”).

Required review UI:
1. Show extracted text and proposed structured fields side-by-side or in a clear review sequence.
2. Highlight uncertain dates, overlapping jobs, missing month/year, ambiguous employer/title order, duplicate skills and inconsistent contact details.
3. Allow the user to edit, accept, skip or discard every proposed field.
4. Do not save facts or generate a resume until the user confirms the import proposal.
5. Preserve the original upload text as source evidence only as long as the user has explicitly chosen to retain it; otherwise keep it transient and discard it after the request.
6. Show a clear parse failure state with manual-entry path; never leave a spinner or pretend an empty parse succeeded.

### 4.3 OCR decision gate

Scanned PDFs are not currently supported. Investigate an optional local OCR path, but do not silently add a large model or hosted OCR service.

- `naptha/tesseract.js` is Apache-2.0 and runs OCR in Node/browser through WebAssembly, but its official documentation says it does **not parse PDF files**. PDF pages must first be safely rasterized with an independently audited PDF renderer. OCR model/language data must also be licensed, pinned and documented separately.
- `tesseract-ocr/tesseract` is Apache-2.0; its trained language data is a separate artifact and must be tracked/verified too.
- Before adopting OCR, benchmark English and at least one Indic script relevant to Folio users, plus Arabic/RTL where the language assets support it. Record speed, peak memory, extraction accuracy and package/model size on CPU-only low-spec hardware.
- OCR should run only for scanned/image-only pages or with user opt-in when text extraction is poor. Never replace good embedded text with a lower-quality OCR result.
- Return page-level confidence and an explicit “review carefully” state. OCR is not a fact verifier.
- If the safe PDF rasterization/OCR path cannot be delivered within time/resource limits, ship scan detection plus the current honest unsupported message. Do not claim OCR support.

### 4.4 Source-fact ledger and anti-fabrication

- Keep the original `factsJson` source snapshot separate from generated `dataJson`.
- Add precise provenance pointers to the extracted evidence; user-confirmed facts override extraction proposals.
- Tighten entity checking so fuzzy token overlap cannot incorrectly validate unrelated companies, degrees or skills. Use normalized exact/alias matching and source-snippet evidence; any unresolved case becomes a review warning.
- A metric is permitted only when an explicit source fact supports the exact number and unit. Never manufacture percentages, revenue, savings, team sizes, budgets, volume, accuracy, ranking or time saved.
- If the user asks to add a missing skill, ask them to confirm the skill and experience level; never infer it from a job description alone.
- Preserve every source fact even when it is irrelevant to a particular target job. Tailoring can de-emphasize a fact, not delete it from the master document.

## 5. M33.5-B — ATS readability and job-description analysis

### 5.1 Two different reports, never one mysterious score

Implement two separate deterministic reports:

**A. Document Readability Report** — assesses whether the generated/uploaded file has extractable, orderly text and common structural risk factors.

**B. Job Requirement Evidence Map** — compares the job description with explicit user-confirmed resume facts and shows which requirements have evidence.

These reports answer different questions. Do not combine them into an arbitrary “ATS score” or infer a hiring decision.

### 5.2 Document Readability Report

Use a versioned report schema with:
- `status`: `good`, `review`, `problem`, or `not-run`;
- `checks[]`: stable check id, category, status, severity, measured evidence, remediation and evaluator version;
- `untested[]`: what the product cannot know (specific ATS vendor behaviour, employer configuration, recruiter preferences, proprietary ranking rules);
- `fileFacts`: file type, decoded page count, text character count, text extraction result, reading-order signals, selectable-text result where measurable;
- `evaluatedAt` and `reportVersion`.

Deterministic checks should include (only where actually measurable):
1. Selectable/searchable text exists in every expected page; image-only pages are identified.
2. Name and selected contact fields appear in extracted text, without copying PII into logs.
3. Section headings are recognizable and hierarchy/order is coherent.
4. Reading order is plausible; suspicious column/table/header/footer patterns are flagged for review, not automatically failed.
5. Text is not fragmented character-by-character or split by excessive spaces.
6. Dates and chronology are parseable and internally consistent; overlaps are warnings, not assumed errors (multiple jobs can overlap).
7. URLs are text-readable and not present only as a decorative icon.
8. PDF text is not a single raster image; fonts/characters do not produce replacement glyphs or empty extraction.
9. DOCX structure uses semantic paragraphs/headings/bullets rather than text boxes or decorative objects wherever the renderer controls the file.
10. Document length/page count is a configurable advisory, never a fixed global rule for every profession or academic CV.
11. Standard single-column ATS template checks: no layout tables, text boxes or essential content placed only in headers/footers; other creative templates receive transparent layout warnings, not a false guarantee.
12. Export text round-trip: extract text from the final PDF/DOCX and compare key facts and reading order with the saved `ResumeData`; show missing/altered text before download.

Rules:
- A report can say “these measurable checks passed”; it cannot say “all ATS systems will parse this correctly”.
- Show each finding and why it matters. Do not hide negative findings behind a numeric grade.
- Provide a clearly labelled “ATS-friendly layout” export using the existing single-column template, with semantic, selectable text and conventional headings.
- Maintain creative layouts as a separate user choice; do not force all professions into one design.
- Provide an export verification status for the exact generated bytes. If it cannot be decoded/re-read, say so and do not mark export verified.

### 5.3 Job Description parser and evidence map

Input remains a user-pasted job description in this milestone unless a safe file intake path is explicitly implemented and tested. The job description is untrusted source content, not instructions.

Create a typed, versioned `JobRequirementProfile` containing:
- role title and organization only when actually present;
- required vs preferred qualifications;
- skills/tools/technologies;
- role responsibilities;
- education/licensing/certification requirements;
- seniority/experience range only when explicitly stated;
- language/location/work-mode requirements when explicit;
- exact source phrases and bounded evidence spans from the job description.

Compare each requirement with the user's confirmed facts:
- `supported`: direct resume evidence exists;
- `partial`: related but incomplete evidence exists;
- `missing`: no evidence was found;
- `not_assessable`: ambiguous, conflicting or impossible to assess.

Each match must cite the resume fact(s) supporting it. For partial/missing requirements, offer questions to the user rather than adding the requirement as a claimed skill.

Matching rules:
- exact phrase and controlled alias/synonym mapping are explainable and testable;
- do not rely on substring matches that create false positives (e.g. `Java` vs `JavaScript`);
- preserve negation and proficiency context ("basic exposure" is not "expert");
- preserve years of experience only when the dates allow a transparent calculation; do not infer continuous employment across gaps;
- distinguish mandatory requirements from preferred requirements;
- allow the user to correct parsed requirements before analysis;
- show weighted coverage only as a descriptive calculation with published formula and no probability interpretation;
- do not encourage keyword stuffing or white/invisible text.

### 5.4 Tailoring must not destroy the master resume

The existing `tailorResume()` updates the current `LaxiiResume` row. M33.5 must add a safe **Create tailored copy** path:

1. Keep the master resume unchanged.
2. Create a new resume conversation/document variant linked to the source master (or implement a version model after schema review).
3. Tailor only summary, skills ordering and relevant existing work/project bullets where source evidence supports it.
4. Preserve all source facts in the new variant's facts snapshot.
5. Show a before/after diff and exact facts removed/de-emphasized/reworded.
6. Never add JD-only skills or achievements to the resume.
7. Store target role, company (only if supplied), job description fingerprint/hash and creation time; do not save full JD text without an explicit retention reason and privacy notice.
8. Make it possible to return to the master and earlier variants.

## 6. M33.5-C — First-class Cover Letter Studio

### 6.1 Document model

A cover letter is a document, not a resume summary. Create its own validated schema and private persistence path. Suggested fields:

- `schemaVersion`;
- `basics` (sender identity/contact references from the user's confirmed facts);
- `targetRole`;
- `companyName` (empty unless user supplied or clearly extracted and confirmed);
- `hiringContactName` (empty unless confirmed; never invent "Dear Hiring Manager" name);
- `date` (user-selected or deterministic current date at generation time, clearly editable);
- `salutation`;
- `opening`;
- `bodyParagraphs[]`;
- `closing`;
- `signatureName`;
- `tone` (`formal`, `confident`, `warm`, `direct`, `creative`, `academic`);
- `wordCount` and structured provenance metadata;
- `resumeConversationId`/source resume id when linked;
- `jobDescriptionHash` and optional source reference (avoid unnecessary duplicate storage of sensitive JD text);
- `createdAt`, `updatedAt`, `version`.

Keep body paragraphs as selectable text. Do not render a letter as an image.

### 6.2 Generation behaviour

- Generate from user-confirmed career facts + optional saved resume variant + the exact target job description.
- Focus on 2–3 relevant pieces of evidence from the candidate's actual background; avoid repeating the entire resume.
- Do not invent company praise, mission statements, hiring manager identity, relationships, referrals, personal stories, achievements or metrics.
- If no company name or contact is available, use a neutral greeting or let the user choose; label placeholders explicitly.
- If a requirement is unsupported by the user's resume, ask a question or omit it. Never claim the candidate has it.
- Offer configurable length and tone; default to a concise, human-sounding one-page letter without claiming that one length works for every country/employer.
- Avoid generic hype, excessive adjectives, fake enthusiasm, canned claims and keyword stuffing.
- Preserve exact proper nouns and facts. Run the same entity/skill anti-fabrication checks as resumes, extended to the letter.
- AI edits must carry a provenance badge; user edits are not labelled AI-generated.
- Provide actions: create draft, rephrase selected paragraph, adjust tone/length, regenerate selected paragraph, save, duplicate, compare and export.

### 6.3 Separate storage and API

- Inspect the current Prisma relation first: `LaxiiConversation.kind` is a string with existing kinds and `LaxiiResume` is one-to-one with a resume conversation.
- Prefer an additive `LaxiiCoverLetter` model related one-to-one to a dedicated `LaxiiConversation` (`kind = COVER_LETTER`) or a similarly isolated additive design. Do not overload `LaxiiResume.dataJson` with cover-letter JSON.
- Add only necessary indexes and unique constraints. Keep owner id on the row and verify it on every read, write, version and export.
- Add schema validation, idempotent request handling where needed, rate limits, AI consent/quota gates and private `no-store` responses.
- Never introduce public URLs or unprotected file storage for letters.
- No database migration against production in M33.5 development. Use the QA database guard and document migration/rollback steps for a later owner-authorized deployment.

Suggested routes (adapt to the existing conventions after inspection):
- `GET /api/laxii/cover-letter` — user's private library/detail;
- `POST /api/laxii/cover-letter` — generate or duplicate a draft;
- `PATCH /api/laxii/cover-letter` — save confirmed edits;
- `POST /api/laxii/cover-letter/export` — PDF/DOCX export;
- optional `POST /api/laxii/cover-letter/rephrase` or action-discriminated POST for editing.

Do not create every route if the existing API convention can express the same secure lifecycle more simply.

### 6.4 Export and preview

- Reuse existing PDFKit and `docx` dependencies after testing layout; do not add another document rendering stack without a measured need.
- Generate professional letter templates consistent with Resume Studio's existing styles, but use letter-appropriate margins, spacing, date, addressee and signature layout.
- Keep text selectable and ordered.
- Verify the exact PDF/DOCX bytes by decoding/reopening, extracting text and checking exact names/paragraphs/order.
- Ensure page breaks do not split headings or signature awkwardly; avoid blank trailing pages.
- Export file name must be sanitized and response must use safe content type, `Content-Disposition` and `Cache-Control: no-store`.

## 7. M33.5-D — Career document versions and library

- Keep one master resume distinct from job-specific variants.
- Save a new tailored copy rather than overwriting the source master.
- Add an explicit revision/variant history that records source document, parent revision, target title, selected format, created time, user/AI provenance and content hash.
- If adding a `LaxiiResumeRevision` or `LaxiiCareerDocumentVersion` model, make it additive and bounded (e.g. retain a documented maximum number of snapshots per document); pruning must never delete the current master or user-pinned version.
- Version creation and `LaxiiResume` updates must be transactional to avoid an overwritten document with no recoverable snapshot.
- Provide compare and restore. Restore must create a new revision or preserve the current state first; never silently erase a newer document.
- Cover letters also need named variants/versions (e.g. company/role/date) and duplication from a previous draft.
- Provide a private library grouped by master resumes, tailored resumes, cover letters and imported source materials. Search/filter by job title/company/date only over data the user owns.
- Avoid adding a brand-new global Career Documents navigation item if the current LAXII Resume Studio can support the feature without UI disruption. Any navigation change requires a specific user-facing need and separate review.

### 9.1 Vendor evidence and ATS honesty

Official help documents from real ATS vendors show that supported formats and parsing behaviour are vendor-specific. Lever documents support for Word/PDF and says image files are not parsed as resume text; Greenhouse documents parsing failures related to complex layouts, graphics, tables, headers/footers and columns. These are examples, not universal rules.

Therefore:
- Do not claim to emulate Greenhouse, Lever, Workable or every vendor's proprietary parser.
- Build reproducible local checks and export round-trip tests.
- Maintain a curated test-fixture corpus of selectable-text PDF, DOCX, scanned PDF, multi-column resume, academic CV and multilingual resume (synthetic names/facts only).
- The report must name its evaluator version and say it is a practical diagnostic, not an employer ATS simulation.

### 9.2 Licence controls

Before adding any project/dependency/model/data:
- pin exact release/commit;
- record source URL, copyright owner, licence text/hash, transitive licences and commercial-use status;
- inspect model and traineddata licences independently of package code;
- add the result to `docs/oss/THIRD_PARTY_COMPONENTS.md`;
- avoid GPL/AGPL or source-available/restricted code unless the repository owner has explicitly reviewed the legal implications;
- keep OCR optional and disabled when its local runtime/assets are absent.

## 10. Security, privacy and reliability

### 10.1 Upload threat model

- Verify signature, size, file type, page count, archive entry count, decompressed bytes and parser time.
- Reject encrypted/password-protected files with an honest user-facing message; never ask for a password in telemetry.
- Handle malformed PDFs, malformed DOCX ZIPs, nested archives and decompression bombs safely.
- Sanitize all text and remove unsafe control characters while preserving Unicode and scripts.
- Never dereference remote images, URLs, XML external entities or embedded resources during parsing.
- Use timeouts and memory ceilings; kill or abandon worker tasks safely.
- Prevent temp-file leaks; use private, per-request temp directories and cleanup in `finally` paths.
- Keep uploaded documents private to their owner. No cross-user existence leak: return 404 for another user's document id.

### 10.2 AI and prompt injection

- Resume text and job descriptions are untrusted content. Explicitly delimit them as data in prompts.
- System policy must say ignore commands inside imported documents/JDs and never reveal prompts, secrets or other users' data.
- Do not let imported text modify tools, call URLs, alter system instructions or trigger automations.
- All generated entities/skills/metrics must be validated against the confirmed source-fact ledger.
- Failed validation means no generated draft/letter is saved. A bounded corrective retry is allowed only if existing policy supports it; no infinite retry loop.

### 10.3 User data lifecycle

- Do not store raw files in a public bucket or public MediaAsset path.
- If original files are saved, use existing owner-scoped private storage with explicit user choice, strict path/ownership validation and delete controls.
- Keep logs metadata-only. Avoid document contents, PII, raw source snippets and full job descriptions in logs.
- Keep export responses private/no-store.
- Document deletion must remove or safely detach private snapshots/versions according to existing cascade semantics; no orphan document records.

### 10.4 API and persistence

- Require authenticated owner session on every endpoint.
- Check owner id on every referenced resume, version, source file and cover letter.
- Apply existing rate limits and `aiGate` consent/quota flow to every AI operation.
- Use Zod schemas and request size caps; do not accept arbitrary JSON blobs without schema validation.
- Use transactions for create conversation + document rows, revision snapshots + updates and restore.
- Use compare-and-swap/version ids or update timestamps to prevent concurrent saves from silently overwriting the user's newer edits.
- New queue/worker behaviour must have idempotency keys and clear terminal failure states; no duplicate generation after retries.

## 11. Test and evidence matrix

### 11.1 Import and extraction

- PDF with selectable text; image-only scanned PDF; mixed scanned/text pages; corrupted PDF; encrypted PDF; very large page count; DOCX with headings, bullets and tables; malformed DOCX ZIP; TXT/MD; unsupported extensions; MIME/signature mismatch; Unicode names; Devanagari; Arabic/RTL; combining marks.
- Verify size/page/decompression/character limits and deterministic truncation metadata.
- Verify parse endpoint is private, rate-limited, non-persistent and cleans temporary files on success/failure.
- Verify structured proposal preserves every extracted fact and flags ambiguity rather than filling it.
- Verify import review requires confirmation before facts are saved/used.

### 11.2 Anti-fabrication and tailoring

- Synthetic fixture with known employers, institutions, dates, metrics and skills.
- Prompt-injection strings embedded in source text and job description must not alter policy.
- Unsupported employer, degree, certificate, skill or metric must be rejected/dropped with explicit note.
- Similar token false positives (Java/JavaScript, C/C++, RN/React Native, AWS/AWS Certified) must not count as exact evidence without a curated alias.
- Partial proficiency, expired qualifications and overlapping jobs must preserve context.
- Tailored-copy operation never mutates master; restoring older copy cannot destroy current one.

### 11.3 ATS/readability report

- Each check has deterministic fixtures for pass/warn/fail/not-run.
- Report schema version is stable; evidence text is bounded and PII-redacted for logs.
- Report explicitly lists unsupported/unobservable vendor-specific behaviour.
- PDF/DOCX round-trip extraction verifies exact names, dates, companies, headings, bullet content and reading order.
- Multi-column creative template triggers transparent layout diagnostics without being categorically rejected for every job.
- Academic CV with many pages/publications is not punished by arbitrary one-page rules.

### 11.4 Cover letters

- No employer/person/achievement/metric outside confirmed facts and supplied job text.
- Missing company/hiring manager remains blank or uses user-approved neutral greeting.
- Tone and word-length controls work; user edits survive save/reload/export.
- Rephrase one paragraph does not mutate other paragraphs or facts.
- Linked resume id must be owner-owned; foreign id gives 404.
- PDF/DOCX output is selectable, correctly ordered, no blank trailing page, safe filename and no-store.

### 11.5 UI/browser

- Real browser flow: import → review → confirm → generate → edit → analysis → tailor-copy → cover letter → save → reload → export.
- Test desktop 1440, tablet 768/1024 and mobile 390.
- No overflow, console errors, unhandled requests, dead controls, inaccessible dialogs or broken preview.
- Capture before/after screenshots for all newly modified surfaces.

### 11.6 Repository QA

Run focused tests, then full QA as permitted by repo guidance, with baseline comparison for known parallel DB contention. Also run:
- `bunx tsc --noEmit`;
- `bun run lint`;
- production build;
- Prisma validate + schema parity if schema changes;
- route/auth ownership tests;
- secret/runtime-data scans;
- dependency and licence audit.

Never hide baseline flakes by weakening tests. Classify exact failing tests against untouched baseline under the same suite combination and isolated runs.

## 13. Definition of Done

M33.5 is complete only when:

1. Existing 17 resume formats, 26 profession families, current import types, editable fields and PDF/DOCX exports still work.
2. Import yields a reviewable structured proposal or an honest parse failure; no unconfirmed extraction is stored as verified fact.
3. ATS-readability checks have deterministic evidence and explicit `untested` limits; no universal ATS compatibility claim exists.
4. Job matching is an explainable evidence map against confirmed facts, not a prediction of recruitment outcome.
5. Tailoring creates a new copy and preserves the master source document.
6. Cover letters are first-class private editable documents with provenance and no invented details.
7. Resume and cover-letter exports are decoded/re-read and checked for exact text integrity.
8. Owner scoping, consent, quota, rate limiting, no-store, privacy and upload threat controls are covered by tests.
9. Browser flows and screenshots verify desktop and mobile behaviour.
10. Capability matrix and OSS register accurately reflect implementation and licences.
11. Typecheck, lint, production build and focused tests pass; full QA failures are honestly baseline-classified.
12. No production DB, deployments, DNS, paid services or live user content were changed.
13. Changes are committed/published only through `scripts/ops/bean-sync.sh` normal fast-forward workflow; open PR for owner review; never self-merge.
