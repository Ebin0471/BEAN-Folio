## 3. Fix A — allowlist stored quality-report output

**Problem (independent M36.7 review):** `validateStoredQualityReport()` validated required fields but returned `raw as QualityReport` — the ORIGINAL stored object. Unexpected properties at the top level, inside any finding, or inside the optional `aiReview` block (and its findings) survived validation and entered the tool response (`qualityEvidence.report`), and `JSON.stringify` of the whole result shipped them.

**Correction (exact `QualityReport` type honored):** the validator keeps the existing compatibility rules verbatim (`overall` ∈ pass/warn/fail; `evaluator` ∈ deterministic / deterministic+ai-review; non-empty `evaluatedAt` string; findings array ≤ 200 with per-finding id/area/status/check/measured/note rules; optional `aiReview` with `ran === true`, note ≤ 600, findings ≤ 8 with area/severity/note rules) and then builds a NEW object from explicitly approved fields only:

- top level: `overall`, `findings` (rebuilt array), `evaluator`, `aiReview` (only when a valid block exists), `evaluatedAt` — no spread of `r`;
- each finding: `id`, `area`, `status`, `check`, plus `measured`/`note` ONLY when a valid string is stored (optional fields stay optional — a clean finding gains no phantom keys);
- `aiReview`: rebuilt as `{ ran: true, findings: [...rebuilt], note }`;
- each aiReview finding: `area`, `severity`, `note` only.

Raw stored objects are never spread or passed through at any level. Legitimate stored reports reconstruct field-for-field, so `refinementDirectives(report)` (which reads finding `id`/`status`) and the evaluator/aiReview advisory notes behave exactly as before. The honest handling of missing, malformed, RUNNING and FAILED reports is untouched — those paths never reach the rebuild. Internal provider metadata, unexpected keys and arbitrary stored properties cannot enter the response (proven by tests planting hostile extras at all three nesting levels).

## 4. Fix B — require an assistant-generated LAXII job

**Problem (independent M36.7 review):** the owner-scoped message lookup used `where: { id, conversation: { userId } }` with no role constraint, so a user's OWN `USER`-role message (or a `SYSTEM` row) carrying a plausible `qualityReport` in `metaJson` would be interpreted as a completed generation job — status read, report surfaced — even though it is not an assistant-generated LAXII job.

**Correction:** the existing database lookup now enforces `where: { id: messageId, role: "ASSISTANT", conversation: { userId: ctx.userId } }` — the same constraint the existing LAXII job lookups enforce (`src/lib/laxii/service.ts` `getJob`/`listJobs`/`retryJob` use `role: "ASSISTANT"` in their owner-scoped `where` clauses). This is the task's preferred placement (enforcement inside the existing DB query, compatible with the schema — `LaxiiMessage.role` is a plain string column, USER | ASSISTANT | SYSTEM). An owned USER/SYSTEM message is therefore indistinguishable from a missing/foreign row and receives the ONE generic refusal (`"No accessible LAXII record exists for this request — nothing was analyzed."`) — safe (no existence/role probing of others' rows) and consistent with the established foreign≡missing equivalence. The ownership boundary through the owning conversation is unchanged, job-status semantics (RUNNING / FAILED / DONE honesty) are unchanged, and no new refusal branch was added.
