## The flaw corrected

The previous Finding 3 text (§11 A.3) claimed PostgreSQL's default READ COMMITTED plus an in-transaction re-read was sufficient to serialize concurrent consent grants. That reasoning was UNSOUND: two transactions that both observe no current grant can each insert a separate GRANTED row under READ COMMITTED, producing two simultaneously-current grants — a violation of the §2.3 current-consent invariant. The claim is retracted in place and the contract is corrected.

## The corrected contract (§A.3)

- Every workforce consent-lifecycle transaction explicitly requests `Prisma.TransactionIsolationLevel.Serializable` — verified requestable on BOTH providers for the pinned Prisma version (Prisma 6 documentation, `apps/docs/content/docs/orm/v6/prisma-client/queries/transactions.mdx` supported-levels table: PostgreSQL ✔️ / SQLite only-Serializable; matching per-provider generated client surface of the installed resolution 6.19.2 under `^6.11.1` pins).
- The entire consent decision and write (fresh read, write, strict audit) stays in the SAME interactive transaction; explicit `maxWait`/`timeout` are set.
- Retry ONLY verified conflict/serialization/transaction-timeout errors — `P2034` (pinned v6 error reference: "Transaction failed due to a write conflict or a deadlock") plus, on SQLite, `P1008`/`P2028`, the OBSERVED surfacing of serialization waits in planning-time disposable-DB probes (P2034 was never observed on SQLite in-process); the retryable set is a fixed, documented constant; NO other error is retried.
- Each retry re-runs the ENTIRE transaction callback in a NEW transaction including the fresh current-consent read; bounded to three attempts; retry exhaustion returns an explicit failure — a conflicted or exhausted operation NEVER reports success; truthful idempotency and default-deny behavior preserved.
- Documented fallback (only if Serializable cannot be safely established at implementation time): a database-enforced partial unique index on current GRANTED rows — requires raw migration SQL outside the additive no-migration boundary, so it needs a separate owner-authorized migration decision. No invented row locks, advisory locks, or Prisma capabilities.
