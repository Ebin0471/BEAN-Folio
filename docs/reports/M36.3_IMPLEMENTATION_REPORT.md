## 5. Implementation details

### 5.1 `ox.match.explain` (LOW / Level 1 / discovery / read-only)

- **Input:** strict Zod `{ opportunityId? | opportunityRef?, candidateUserId }` — exactly one locator; `opportunityRef` is the M36.2 typed reference resolved by the engine before execution (plan-time rule: it may only name an explicit earlier dependency).
- **Authorization (exact match-route chain, fresh per execution):** workspace hint → `requireOrgRole(orgId, userId, OWNER/ADMIN/RECRUITER)` (the routes' discovery role trio; VIEWER and HIRING_MANAGER denied) → `getOrg` + refuse SUSPENDED + require VERIFIED → tenant-bound opportunity lookup (`id + organizationId`) → foreign/unknown opportunity = honest no-match (existence-hiding, no content leak).
- **Lifecycle dispatch (route parity):** PUBLISHED → stored row REQUIRED (`matchVersion === OX_MATCH_VERSION`, unexpired, `eligible`) else truthful `MATCH_REFRESH_REQUIRED` (zero writes, never a scan); PAUSED → FROZEN stored rows; FILLED/CLOSED → TERMINAL stored rows; DRAFT/PENDING_REVIEW → requirement-readiness info ONLY — the candidateUserId is deliberately never read in those states (proved by a test with a nonexistent candidate id).
- **Fresh discoverability before ANY disclosure:** `assertCandidateDiscoverableToOrg` with `getOrgActiveMemberUserIds` — consent ledger re-read, ACTIVE visibility, blocks both directions vs ACTIVE members, demo/deleted excluded, employment + disclosed-compensation hard filters unchanged. Failure ⇒ masked card via the EXISTING `serializeMatchForEmployer` + `maskedStateFor` (no candidate content, no explanation) and NO disclosure audit.
- **Explanation output:** the canonical match card (route parity incl. the viewer serializer and `activeInviteExists`) + narration derived ONLY from the stored explanation and fresh read-only reads: skill coverage (covered/missing labels from the same id sets the engine scored), profession alignment, evidence availability (fresh PUBLIC+PUBLISHED count), work-mode/location/availability/compensation factor states with real reasons, missing-information list mapped from not-applied factor reasons, deterministic employer-owned questions, limitations (score semantics + experience exclusion + state honesty), provenance (engine version + stored-row generatedAt/expiresAt).
- **AI verification questions (advisory only):** fresh `resolveCurrentAiProcessingConsent(candidateUserId)` gates the single gateway call; prompt carries only already-disclosed match data (no experience fields) wrapped as UNTRUSTED DATA with an absolute no-accept/no-reject/no-protected-attribute/no-rescoring contract; strict output schema rejects invalid output (deterministic explanation stands); gateway failure degrades honestly. Without consent: NO gateway call, generic unavailability note, private consent state never disclosed.
- **Audit:** authorized disclosure records `ox.candidate.viewed` (`OX_TARGET.candidateProfile`) with organizationId/opportunityId/candidateUserId/purpose DISCOVERY + `via: "riishe:ox.match.explain"`; masked/refused/refresh-required/requirements-only responses fabricate no disclosure audit (tested). The registry declares its own `riishe.tool.ox_match_explain` (recorded by the engine for every execution).
- **`matchId`** is emitted ONLY on authorized disclosure outcomes (LIVE/FROZEN/TERMINAL) — the typed producer value.

### 5.2 Candidate-scope `portfolio.evidenceReport` (same registered tool)

- **Input:** `subject` becomes a discriminated union — `{ kind: "self" }` byte-unchanged; `{ kind: "candidate", candidateUserId }` requires an opportunity locator (`opportunityId` or `opportunityRef`); self + locator is rejected; strict mode rejects every other selector.
- **Authorization chain (ALL fresh, per execution):** ORGANIZATION workspace hint → ACTIVE OWNER/ADMIN/RECRUITER (`requireOrgRole` + `OX_OPPORTUNITY_WRITE_ROLES`) → VERIFIED non-SUSPENDED org → tenant-owned opportunity → **PUBLISHED only** (the sole state that permits candidate discovery — D6; draft/pending states never match) → fresh `assertCandidateDiscoverableToOrg` → fresh `resolveCurrentAiProcessingConsent` (current `OX_CONSENT_VERSION`). Employer-side failures keep clear reasons; **candidate-side failures (discovery boundary OR consent) return ONE generic `CANDIDATE_UNAVAILABLE` outcome** — zero candidate content, zero gateway calls, no disclosure audit, and the private consent state is never revealed.
- **Evidence sources (binding §10.1):** declared profile fields (headline/availability/location), declared professions + taxonomy skills, viewer-safe profile fields (employment types, work modes, preferred locations, experience fields as DECLARED data — never matching factors, never qualification judgments), fresh PUBLIC + PUBLISHED + non-archived projects only (`publicProjectStatusFilter` + `publicOwnerFilter`), account-level `TrustVerification` rows with status VERIFIED (kind/status/review date only). Structurally absent: contact data, compensation values, private/unlisted/draft/archived work, private documents, per-skill/per-project verification.
- **Evidence ladder:** DECLARED / DEMONSTRATED / VERIFIED / UNKNOWN preserved exactly; a public project tag demonstrates, never verifies; againstRole comparison is deterministic evidence-level narration (no scores).
- **AI layer:** reached only when every gate passed; grounded narration over THIS request's evidence; strict contract; failure → deterministic report stands; nothing AI-derived is persisted or cached.
- **Self branch:** unchanged (deterministic, zero AI calls — tested).

### 5.3 Typed `matchRef`

- `REF_FIELDS` += `matchRef`, `REF_RESULT_KEYS.matchRef = "matchId"`; producer `ox.match.explain`; M35.7 plan-time rules apply unchanged (no self/forward refs, explicit dependency declaration, earlier-step ordering).
- Resolution-time enforcement (`resolveStepParams` additive branch → `verifyMatchRefAuthorization`): row exists → opportunity exists + tenant org → ACTIVE OWNER/ADMIN/RECRUITER membership of the WORKFLOW OWNER in THAT org (derived from the row, never from a client/model id) → org VERIFIED + not SUSPENDED → fresh `assertCandidateDiscoverableToOrg` (DISCOVERY consent inside). Failures throw `WorkflowError(…, "authorization-revoked")` — revocation, blocks, role loss, suspension and lost opportunity access between producer and consumer all fail the resolution (each tested).
- M36.4 consumers (invitation preparation, room brief) inherit the duty: the pointer is never permission. No consumer tool was implemented in M36.3 (per the milestone boundary).

### 5.4 Specialist, planner and routing

- `talent-intelligence`: ORGANIZATION-only; tools `[ox.match.explain, portfolio.evidenceReport]`; `available()` re-verifies both registrations; multi-word routing keywords only.
- `classifySpecialist`: match-explanation language routes to TI in ORGANIZATION workspaces; PERSONAL never selects it; "find candidates…" stays Talent Scout; hiring-draft language stays Workforce Strategist; personal discovery stays People Finder; portfolio self-review stays Portfolio Intelligence (all asserted).
- Deterministic planner: the TI clause plans a step ONLY with explicit `candidate <id>` AND `opportunity <id>` tokens (never invented); explain-language without an explicit selection produces no step; explicit-id clauses are protected from the broad opportunity-radar intent by a narrow additive guard (all other clauses keep the historic path).
- LLM planner catalog: the specialist catalog and tool catalog are live-derived; `matchRef` added to the planner's reference-params enumeration.
