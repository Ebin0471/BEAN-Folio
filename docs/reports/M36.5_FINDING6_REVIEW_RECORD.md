## What was clarified (three findings)

1. **Retry classification tightened (§A.3 rule 3).** The previous contract retried SQLite `P1008`/`P2028` by error code. That was UNSAFE: both are broad categories (`P1008` "Operations timed out after `{time}`"; `P2028` "Transaction API error: `{error}`" — pinned v6 error reference, re-verified), and fresh planning-time probes at this baseline captured the EXACT signatures (code, message, `meta`, nested cause) of 27 contention failures and PROVED them not contention-specific: a single NON-contention slow transaction (zero concurrent writers) produced the IDENTICAL `P2028` "Transaction already closed … expired transaction" signature, and the `P1008` "Socket timeout" variant is a generic stall surface. The SQLite `P1008`/`P2028` contention mappings are therefore marked PENDING and the classifier treats them as non-retryable (fail closed). The only retried error is the documented transaction-conflict error `P2034` (the only code the version-pinned v6 transactions guide gives retry guidance for; runtime confirmation pending §6 item 10). Retry safety for a `P2034` conflict with uncertain commit outcome is claimed ONLY through the contract's required idempotency mechanism, which must also cover audit effects (a re-run resolves an already-committed attempt truthfully — `created: false` / existing declaration row, the §4 `@@unique` constraints blocking duplicates — WITHOUT a duplicate audit row). Maximum of three attempts, whole-callback retries, explicit failure on exhaustion: unchanged.
2. **Serializable isolation explicitly extended to manager-targeted writes (§A.2, §A.3).** The contract now requires the same `Serializable` interactive transaction for every operation that (1) reads the subject's current workforce consent, (2) uses it to authorize the manager-targeted declaration/update, (3) writes the employee workforce record, and (4) writes its strict audit event — explicitly NOT limited to `grantWorkforceConsent`/`revokeWorkforceConsent`. Race semantics: the declaration either serializes first (commits atomically with its audit record) or the revocation serializes first and the manager operation fails its in-transaction consent check — any whole-transaction retry re-reads consent fresh and refuses the declaration (uniform 404). A declaration can never commit after a revocation has made consent non-current. Self-service, role authorization, target-membership validation, and all 404 existence-hiding semantics are unchanged.
3. **Uniqueness fallback flagged NOT ready-to-implement (§A.3 rule 8).** The previously recorded fallback (partial unique index on `status = 'GRANTED'`) was rechecked against expiry semantics and found incompatible: expiry is a resolution-time concept that never updates the row in place, so an expired row KEEPS `status = 'GRANTED'` with `expiresAt` in the past — a status-only predicate would block the legitimate subsequent re-grant. No predicate form is verified to distinguish current from expired GRANTED rows; any database-enforced uniqueness alternative requires a separately authorized migration decision with proven predicate and lifecycle compatibility. No schema or migration change is proposed or authorized here.
