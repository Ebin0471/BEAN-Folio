The approved decision record (§5) permits an implementation plan covering exactly three layers:

## 2. OD-2 — Workforce-analytics consent layer (design)

### 2.1 Storage decision: a NEW dedicated ledger, not a new scope on the candidate table

The plan proposes a new `WorkforceAnalyticsConsent` model rather than adding a scope value to `CandidateVisibilityConsent`. Rationale:

1. The approved design states workforce-analytics consent **must be separate** from candidate DISCOVERY consent, and architecture §16.2 specifies "New consent scope/ledger for employees (distinct from `CandidateVisibilityConsent`) ... No reuse of DISCOVERY."
2. **Keying**: employment is organization-scoped; the same user may be a member of several organizations with different consent states. Workforce consent is therefore per `(organizationId, userId)`. `CandidateVisibilityConsent` is keyed by `userId` alone with no `organizationId` column — reuse would require modifying the existing candidate consent model (a non-additive change to a production consent ledger) or overloading candidate semantics.
3. **Vocabulary isolation**: a separate server-owned `WF_CONSENT_VERSION` means candidate consent-version pinning (`OX_CONSENT_VERSION`) and workforce pinning never interact; candidate consent state can never satisfy a workforce check and vice versa.
4. **Semantic hygiene**: "must not treat organizational membership as employee consent" — a dedicated table makes the distinction auditable and unambiguous at the schema level.

### 2.2 Vocabulary (new constants, proposed `src/lib/wf/consent.ts` + `src/lib/wf/validation.ts`)

- `WF_CONSENT_SCOPES = ["WORKFORCE_ANALYTICS"]` — the single approved purpose. Future workforce purposes append here; candidate scopes are never valid in the workforce ledger.
- `WF_CONSENT_STATUSES = ["GRANTED", "REVOKED"]`; `WF_CONSENT_SOURCES = ["WORKFORCE_SELF_SERVICE"]`; `WF_CONSENT_VERSION = "M36.5-WF-CONSENT-V1"` (server-owned; never accepted from the client — strict zod input schemas only).

### 2.3 Lifecycle (mirrors the candidate ledger invariants)

- **Append-lifecycle history**: one row per grant; revocation updates the current row in place (`status REVOKED` + `revokedAt`); a re-grant creates a NEW row; no prior consent state is ever overwritten.
- **Current consent** = latest row per `(organizationId, userId, scope)` (deterministic `createdAt DESC, id DESC`), valid only while `status` is GRANTED and (`expiresAt` is null or in the future). NO_ROW / REVOKED / EXPIRED / wrong scope all resolve to **NO consent** — explicit default-deny (OD-2 rule 3).
- **Member self-service only**: grant and revoke require `actorUserId === subjectUserId` with the identity taken from the session, never from client input. OWNER/ADMIN (and every other actor) is refused — the approved design grants nobody the right to consent on behalf of an employee.
- **Membership is not consent**: grant/revoke require an ACTIVE `EmployerMembership` in that organization at call time (via the existing `getMembership` check). REMOVED members' historical rows are retained for audit but resolve to NO consent for analytics (enforcement requires ACTIVE membership AND current consent).
- **Truthful operations**: idempotent re-grant against a current grant (`created: false`); revoking when nothing is revocable returns a truthful reason (no fabricated success).
- **Revocation respected by subsequent access** (OD-2 rule 7): every analytics read re-checks consent fresh from the ledger per request — nothing cached, no event-sourced replay, exactly the `specialist-tools` / `portfolio-tools` enforcement pattern.
- **Concurrency contract** (Finding 3, corrected; Finding 6, clarified): every consent-lifecycle operation AND every manager-targeted consent-gated workforce write (§A.2) requests `Prisma.TransactionIsolationLevel.Serializable` (the ONLY isolation level SQLite supports requesting — its default is already `Serializable`; PostgreSQL supports requesting it as well) and runs the whole decision — the fresh consent read, the authorization, the write, and the strict audit — in ONE interactive transaction that re-reads current consent INSIDE the transaction before deciding; only the documented transaction-conflict error `P2034` is retried, always by re-running the ENTIRE transaction (fresh read included) a bounded number of times and then failing explicitly — a conflicted operation never reports success. `P1008`/`P2028` are broad error categories and are NOT retryable by error code: their recorded SQLite signatures are NOT safely attributable to contention, so those mappings are PENDING and fail closed (probe evidence: §A.3). A prior draft of this contract relied on PostgreSQL's default READ COMMITTED plus an in-transaction re-read; that reasoning was UNSOUND (a re-read cannot prevent two transactions that both observe no current grant from each inserting a separate row) and is retracted. Full provider-verified contract, the recorded error signatures, and the explicitly pending PostgreSQL runtime verification: §A.3.

### 2.4 Access rules (the documented OWNER/ADMIN authorization required by OD-2 rule 5)

| Actor | Own declared workforce info | Another member's info (analytics roster) | Consent ledger |
|---|---|---|---|
| Employee (any role, ACTIVE membership) | Self-inspection always allowed (OD-2 rule 4) — own data; consent governs analytics USE, not self-view | Never | Own ledger: inspect FULL history / grant / revoke (self-service) |
| OWNER / ADMIN | Own data as above | **Only while that member has CURRENT `WORKFORCE_ANALYTICS` consent**; members without consent are EXCLUDED from results (per-member exclusion, mirroring the candidate discovery consent gate — not a hard error for the whole query); fresh read per request; every access audited | Current consent state ONLY — the operational minimum, exposed via roster inclusion/exclusion; NO consent-state dump endpoint and NO historical consent access in v1 (§A.5). May NOT grant, revoke, or alter anyone's consent |
| RECRUITER / HIRING_MANAGER / VIEWER | Own data as above | Never | Own ledger only |
| Any actor, foreign organization | Never (404 existence-hiding deny) | Never | Never |

Additional binding rules:

- OWNER/ADMIN roster access additionally passes the existing organization gates (`requireOrgRole(orgId, actor, OX_MANAGER_ROLES)`; org verification gates unchanged where they apply).
- Every OWNER/ADMIN analytics access emits an audit event recording actor, organization, the consented members included, and result count (OD-2 rule 6).
- **No cross-organization benchmarking, ever**: every query is bound to one `organizationId` derived from the caller's verified membership; no aggregate or comparative endpoint exists in this design.
- **Audit durability** (Finding 1): the §2.6 audit events are DURABLE — written via the proposed opt-in strict audit mode (§A.1) inside the same transaction as the documented operation; an audit-write failure fails the operation it documents. Existing OX callers keep the best-effort `auditOX` behavior unchanged.

### 2.5 Enforcement point

Enforcement lives in a new service layer (`src/lib/wf/`), NOT re-implemented in routes — mirroring the `ox/consent.ts` invariant header ("routes must NOT re-implement them"). Routes only authenticate (`getSessionUser`), take `organizationId` from the URL path, and delegate. If a future RIISHE tool ever consumes workforce data, the tool-boundary rule applies unchanged (`ctx.userId` re-verification + `requireOrgRole`).

### 2.6 Audit actions (new constants appended to the existing registries in `src/lib/ox/audit.ts`)

- `wf.consent.granted`, `wf.consent.revoked` (target `WORKFORCE_ANALYTICS_CONSENT`)
- `wf.workforce.info.viewed` (OWNER/ADMIN analytics access; meta: organizationId, member ids included, resultCount)
- `wf.skill.declared`, `wf.skill.updated`, `wf.skill.removed` (target `EMPLOYEE_SKILL`)
- `wf.role_coverage.declared`, `wf.role_coverage.updated`, `wf.role_coverage.removed` (target `EMPLOYEE_ROLE_COVERAGE`)

All events go through the ONE audit store (`AuditEvent`) and the single writer module (`src/lib/ox/audit.ts`). Workforce events use the proposed opt-in strict mode (`auditOXStrict`, §A.1): same writer, same constants, same model — but written inside the operation's own transaction and fail-closed (an audit-write failure fails the operation it documents). Meta always records `organizationId`, `subjectUserId`, `actorUserId`, and the skill/role identifier where relevant.

## 3. OD-4 — Additive storage layer (design)

### 3.1 Models

Two new additive models, both keyed `(organizationId, userId)` per the approved minimum design (§16.2 OD-4):

- **`EmployeeSkill`** — employee-declared skills. `skillId` references the EXISTING `Skill` taxonomy (L235). Resolution matches EXISTING `Skill` rows by slug or exact label via a new `resolveEmployeeSkillIds` mirroring `resolveOpportunitySkillIds` — never upserted, never a competing taxonomy. Unique `(organizationId, userId, skillId)`.
- **`EmployeeRoleCoverage`** — role-coverage declarations. `roleKey` references the EXISTING code-level profession taxonomy (`src/lib/professions/taxonomy.ts` slugs), validated at write time against `flattenTaxonomy()`; never free-form, never a new taxonomy. Unique `(organizationId, userId, roleKey)`.

Both carry `source` (`SELF_DECLARED | OWNER_ADMIN_DECLARED`) and `declaredByUserId` (loose ref, house style) as **provenance only — never verification**. Removal is a hard delete of the declaration row plus an audit event (declarations are self-service data; the audit ledger preserves the history).

### 3.2 Write authorization matrix (OD-4 rules 4–5 via OD-2)

| Operation | Authorization |
|---|---|
| Employee declares/updates/removes OWN rows | ACTIVE `EmployerMembership` in that org (any role); allowed regardless of own consent state (own data, self-service); audited |
| OWNER/ADMIN declares/updates a MEMBER's rows | `requireOrgRole(orgId, actor, OX_MANAGER_ROLES)` **AND** the subject member's CURRENT `WORKFORCE_ANALYTICS` consent (strict reading: OD-4 rule 5 routes modification authorization through the OD-2 rules; modification of an employee's workforce data is an access to employee information for workforce purposes). Refused otherwise with a generic refusal (no existence leak). Audited with actor + subject. The consent check, the declaration write, and the strict audit share ONE Serializable interactive transaction (§A.2; §A.3 applies to this path — it is NOT limited to consent grant/revoke). Manager-targeted API contract: §A.2 |
| OWNER/ADMIN removes a MEMBER's rows | Not provided in v1 (declarations belong to their subject; removal is self-service). Documented as a deliberate limitation |
| RECRUITER / HIRING_MANAGER / VIEWER writes | Never |
| INVITED / SUSPENDED / REMOVED members | Automatically excluded by `requireOrgRole` / `getMembership` status semantics |
| Cross-organization writes | Never — 404 existence-hiding deny |

### 3.3 Consent-aware access and retrieval

- **Self read**: an ACTIVE member always sees their own rows and own consent ledger for that org (OD-2 rule 4).
- **OWNER/ADMIN analytics roster**: single-org read; per-member fresh consent gate with exclusion semantics (§2.4); audited per access.
- **No other read path exists**: no endpoint, service function, or query in this design exposes one member's workforce records to another member, to recruiters, or across organizations.

### 3.4 No automatic VERIFIED evidence (OD-4 rule 6)

- No code path in this milestone creates or updates `TrustVerification` rows, touches `EVIDENCE_LEVELS`, or upgrades any evidence level. Declared data is `SELF_DECLARED` provenance and nothing else.
- A dedicated regression test asserts zero `TrustVerification` writes and unchanged evidence-ladder output after declaration operations (§6).

### 3.5 Preserved semantics

- Candidate portfolio and evidence semantics untouched; `CandidateOpportunityProfile` is never treated as an employee record; candidate consent surfaces (`CandidateVisibilityConsent`, the O2 routes) keep their exact behavior — the workforce layer never reads them and they never read the workforce layer.
- No weakening of any existing membership or tenant-isolation check: `requireOrgRole`, `getMembership`, `orgIsVerified`, `countActiveOwners`, and the 404-deny convention are consumed as-is, never modified.

During implementation, the schema would be applied ONLY via `prisma db push` inside an isolated QA worktree with a pinned `DATABASE_URL` and the `scripts/ops/qa-db-env.sh assert --must-exist` guard — never in the legacy workspace, never against any production database.
```prisma
/// M36.5 OD-2 — Workforce-analytics consent ledger (employee consent; distinct
/// from CandidateVisibilityConsent by approved design: separate table, separate
/// vocabulary, per-(organizationId, userId) keying). Append-lifecycle history:
/// one row per grant; revocation updates that row in place (status REVOKED +
/// revokedAt) and a re-grant creates a NEW row — no prior state is overwritten.
/// Current consent = the latest row per (organizationId, userId, scope); valid
/// only while status GRANTED and (expiresAt is null or in the future). No row
/// at all also means no consent. Organizational membership is NOT consent.
/// Retention (§A.4): append-lifecycle rows persist while the parent user AND
/// organization rows exist; parent deletion cascades these rows (data
/// minimization). History is NOT claimed to be permanent.
model WorkforceAnalyticsConsent {
  id             String    @id @default(cuid())
  organizationId String
  userId         String
  user           User      @relation("workforceConsents", fields: [userId], references: [id], onDelete: Cascade)
  organization   EmployerOrganization @relation("orgWorkforceConsents", fields: [organizationId], references: [id], onDelete: Cascade)
  scope          String // WORKFORCE_ANALYTICS — workforce purposes only; candidate scopes are never valid here
  status         String // GRANTED | REVOKED — one row per grant lifecycle
  consentVersion String // server-owned (WF_CONSENT_VERSION) recorded at grant time
  source         String // server-owned provenance (WORKFORCE_SELF_SERVICE) — never accepted from the client
  grantedAt      DateTime  @default(now())
  revokedAt      DateTime?
  expiresAt      DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([organizationId, userId, scope, createdAt]) // current-consent lookup: latest row per (org, user, scope)
  @@index([organizationId, userId, status])
}

/// M36.5 OD-4 — Additive employee-declared skill record, keyed by
/// (organizationId, userId) per the approved minimum design. skillId references
/// the EXISTING Skill taxonomy — resolution matches existing rows only (never
/// upserted, no competing taxonomy). SELF-DECLARED data only: these rows are
/// never evidence — no code path may create or modify TrustVerification rows or
/// upgrade any evidence level because of them.
/// Retention (§A.4): persist while the parent user AND organization rows
/// exist; parent deletion cascades these rows.
model EmployeeSkill {
  id               String   @id @default(cuid())
  organizationId   String
  userId           String
  user             User     @relation("employeeSkills", fields: [userId], references: [id], onDelete: Cascade)
  organization     EmployerOrganization @relation("orgEmployeeSkills", fields: [organizationId], references: [id], onDelete: Cascade)
  skillId          String
  skill            Skill    @relation(fields: [skillId], references: [id], onDelete: Cascade)
  source           String   @default("SELF_DECLARED") // SELF_DECLARED | OWNER_ADMIN_DECLARED — provenance only, never verification
  declaredByUserId String // actor of the declaration (loose ref — house style)
  note             String?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([organizationId, userId, skillId])
  @@index([organizationId, userId])
  @@index([skillId])
}

/// M36.5 OD-4 — Additive employee role-coverage record, keyed by
/// (organizationId, userId). roleKey references the EXISTING code-level
/// profession taxonomy (src/lib/professions/taxonomy.ts slugs) — validated at
/// write time against the published vocabulary, never free-form, never a new
/// taxonomy. SELF-DECLARED data only (see EmployeeSkill). Retention (§A.4):
/// persist while the parent user AND organization rows exist; parent deletion
/// cascades these rows.
model EmployeeRoleCoverage {
  id               String   @id @default(cuid())
  organizationId   String
  userId           String
  user             User     @relation("employeeRoleCoverage", fields: [userId], references: [id], onDelete: Cascade)
  organization     EmployerOrganization @relation("orgEmployeeRoleCoverage", fields: [organizationId], references: [id], onDelete: Cascade)
  roleKey          String // existing profession-taxonomy slug — validated, never free-form
  source           String   @default("SELF_DECLARED") // SELF_DECLARED | OWNER_ADMIN_DECLARED
  declaredByUserId String
  note             String?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([organizationId, userId, roleKey])
  @@index([organizationId, userId])
  @@index([roleKey])
}
```

- `Skill`: `employeeSkills EmployeeSkill[]`
- `EmployerOrganization`: `orgWorkforceConsents WorkforceAnalyticsConsent[] @relation("orgWorkforceConsents")`, `orgEmployeeSkills EmployeeSkill[] @relation("orgEmployeeSkills")`, `orgEmployeeRoleCoverage EmployeeRoleCoverage[] @relation("orgEmployeeRoleCoverage")`

### A.1 Finding 1 — Required audit durability (strict audit mode)

**Verified ground truth.** `auditOX` (`src/lib/ox/audit.ts` L128–147) is the ONE OX audit writer and is deliberately best-effort: `client.auditEvent.create(...).catch(() => undefined)` (L146) swallows failures — "an audit failure must not fail the action it documents" (L8–9). Its `Client` type already accepts either the global client or an interactive-transaction client (L126). The finding is accurate: this behavior cannot satisfy a "operation and audit succeed or fail together" guarantee.

**Required behavior (all four event classes).**

1. Workforce consent grants and revocations have durable audit records.
2. Employee skill / role-coverage declarations, updates, and removals have durable audit records.
3. OWNER/ADMIN workforce analytics access is audited (the access event is required even though the operation is a read).
4. Required audit writes participate in the SAME transaction as the operation they document; an audit-write failure aborts that transaction, so the operation can never be reported as successful without its audit record.

**Proposed interface (documentation only — NOT implemented; no existing caller changes).**

```ts
// Proposed addition to src/lib/ox/audit.ts — opt-in STRICT variant of the
// SAME single writer. Same AuditEvent row shape, same OX_AUDIT_ACTIONS and
// OX_TARGET constant registries, same model. No competing audit subsystem.
export async function auditOXStrict(
  tx: Parameters<Parameters<typeof db.$transaction>[0]>[0], // REQUIRED — the caller's transaction
  actorUserId: string | null,
  action: string,
  targetType: string,
  targetId: string,
  meta: Record<string, unknown>
): Promise<void>;
// NO `.catch(() => undefined)`: a write failure throws, which rolls back the
// caller's transaction — fail-closed by construction.
```

**Design rules.**

- Single-writer architecture preserved: `auditOXStrict` lives in the same module, writes the same `AuditEvent` model through the passed transaction client, and consumes the same action/target constant registries. It is an opt-in mode on the existing writer, not a second subsystem.
- Alternative evaluated and rejected: adding a `strict` flag parameter to `auditOX` itself — it risks silently changing behavior through shared defaults and complicates every existing call site; a separate opt-in function carries zero risk to existing callers while preserving the single writer.
- Existing `auditOX` callers (all current OX/RIISHE consumers) keep their exact best-effort behavior; this plan modifies no existing caller.
- Workforce services (`src/lib/wf/`) MUST call `auditOXStrict` with the same transaction that performs the consent/skill/coverage write, and MUST write the analytics-access event strictly: the consent-gated roster read runs fail-closed — if the access-audit write fails, the read fails and zero roster data is returned (sensitive access is denied rather than taken unrecorded).

**Tests specified for implementation time** (added to §6 item 9): injected audit-write failure rolls back the associated transaction with zero partial rows and an explicit failure; success writes exactly one strict AuditEvent with the actual actor and subject; failing access-audit refuses the roster read; existing OX audit suites remain green unchanged.

### A.2 Finding 2 — OWNER/ADMIN (manager-targeted) write API contract (with the Finding 6 Serializable transaction requirement)

**Gap acknowledged.** §3.2 permits OWNER/ADMIN to declare/update a consenting member's records, but §5 originally described only `/workforce/me/...` routes. The manager-targeted contract closes the gap.

**Routes (proposed; NOT implemented).**

| Route | Method | Purpose | Body (strict zod; identity never accepted from body) |
|---|---|---|---|
| `/api/employers/[id]/workforce/members/[memberId]/skills` | POST | Declare one skill for the target member | `{ skill: string /* existing-taxonomy slug or exact label */, note?: string }` |
| `/api/employers/[id]/workforce/members/[memberId]/skills/[skillId]` | PATCH | Update the target member's declaration note | `{ note: string }` |
| `/api/employers/[id]/workforce/members/[memberId]/role-coverage` | POST | Declare one role-coverage key for the target member | `{ roleKey: string /* existing profession-taxonomy slug */, note?: string }` |

**Authorization sequence (server-side, in the `src/lib/wf/` service layer; routes only authenticate and delegate — mirroring the verified route conventions of `src/app/api/employers/[id]/members/[memberId]/route.ts`).**

1. **Actor identity**: `getSessionUser()` ONLY — never request data (house rule, `src/lib/ox/authz.ts` L8–9).
2. **Organization identity**: `organizationId` from the URL path param, verified against the caller's active membership via `requireOrgRole(organizationId, actor.id, OX_MANAGER_ROLES)` — null → 404 existence-hiding deny (verified semantics: unknown org / no membership / not ACTIVE / role not OWNER|ADMIN are indistinguishable). OWNER/ADMIN role authorization is enforced server-side; the client cannot elevate.
3. **Target member identity**: explicit `memberId` path param; `getMembership(organizationId, memberId)` must exist AND be ACTIVE → otherwise 404. A foreign, removed, or nonexistent member is indistinguishable — no existence leak.
4. **Actor ≠ subject**: manager routes require `memberId` ≠ actor; a manager declaring their own skills/coverage uses the self-service `/workforce/me/` routes (which require no consent for self writes).
5. **Subject consent**: `getCurrentWorkforceConsent(organizationId, memberId)` must resolve CURRENT, re-checked inside the SAME Serializable interactive transaction as the write — the one transaction that also performs the workforce-record write and the strict audit event (§A.3; the four-step requirement below) → otherwise the request fails with the same uniform 404 shape; the precise reason (absent consent vs unknown member) is never exposed in the response — it IS recorded in the audit event.
6. **Audit**: `auditOXStrict` (§A.1) records the ACTUAL actor and the ACTUAL subject in the same transaction as the write: `meta: { organizationId, subjectUserId: memberId, actorUserId, skillId|roleKey, source: "OWNER_ADMIN_DECLARED" }`.
7. **Failure semantics**: every failed authorization returns 404 existence-hiding deny, uniform across foreign org, non-manager role, inactive target, missing target, and absent consent — no response distinguishes which check failed.
8. **Success response**: the created/updated row with `source: "OWNER_ADMIN_DECLARED"` provenance — no consent-state details beyond what the operation itself demonstrates.
9. **No manager DELETE in v1**: deletion of another member's declarations remains unavailable unless separately approved (unchanged from §3.2).

**Serializable transaction requirement for manager-targeted writes (Finding 6 clarification — the §A.3 contract explicitly extends to this path).** Every manager-targeted declaration/update MUST run the following four steps in the SAME `Serializable` interactive transaction — no step may execute outside it, and the Serializable requirement is NOT limited to `grantWorkforceConsent` / `revokeWorkforceConsent`:

1. Reads the subject employee's CURRENT workforce consent (`getCurrentWorkforceConsent` — a fresh read inside the transaction, never a pre-transaction cached result).
2. Uses that consent to authorize the manager-targeted declaration or update (authorization sequence steps 2–5 above).
3. Writes the employee workforce record (`EmployeeSkill` / `EmployeeRoleCoverage`).
4. Writes its required strict audit event (`auditOXStrict`, §A.1).

Race semantics against the subject's self-service revocation have exactly two valid outcomes: (a) the declaration serializes FIRST, while consent is current, and commits atomically with its audit record; (b) the revocation serializes FIRST, consent is no longer current, the manager operation fails its in-transaction consent check, and (per §A.3 rule 4) any whole-transaction retry re-reads consent fresh and REFUSES the declaration again — the refusal surfaces as the uniform 404 existence-hiding deny of step 7. A declaration can NEVER commit after a revocation has made the subject's consent non-current, and no partial declaration row or orphan audit event can survive a lost race. Self-service behavior, manager role authorization, target-membership validation, and every 404 existence-hiding semantic of steps 1–9 are unchanged by this requirement.

### A.3 Finding 3 — Concurrent consent-lifecycle operations (CORRECTED contract; Finding 6 clarification; verified provider facts)

**Correction of record.** The previous draft of this section claimed that on the PostgreSQL deployment variant "default READ COMMITTED, where the in-transaction re-read performed after a conflicting transaction's commit observes that committed state" was sufficient to serialize concurrent grants. That claim was UNSOUND and is retracted: under READ COMMITTED, two transactions that both read "no current grant" and then each insert a new GRANTED row can BOTH commit (neither blocks the other; a re-read only helps if it happens AFTER the conflicting transaction commits, which nothing in the design guaranteed). The result would be two simultaneously-current GRANTED rows for the same `(organizationId, userId, scope)` — a violation of the §2.3 current-consent invariant. The corrected contract below closes that window with `Serializable` isolation, which IS requestable on both providers for the pinned Prisma version, verified as follows.

**Verified ground truth (re-checked at correction baseline `1dcac3f` and re-verified at the Finding 6 clarification baseline `5805e99`; nothing relies on prior reports).**

- Development/QA provider of record: **SQLite** (`prisma/schema.prisma` L13, `provider = "sqlite"`, pinned `DATABASE_URL`). Please retry your transaction" — the documented normalized transaction-conflict error, and the ONLY error code the version-pinned transactions guide gives a retry recipe for. `P1008` = "Operations timed out after `{time}`" — a BROAD category: any operation timeout, with no contention-specific qualifier anywhere in the reference. `P2028` = "Transaction API error: `{error}`" — likewise BROAD: a catch-all for transaction-API lifecycle failures with the underlying error embedded as a string. `P2024` = connection-pool timeout (a distinct, non-conflict failure). The breadth of `P1008`/`P2028` is precisely why neither may be retried by error code alone (Finding 6).
- **Planning-time SQLite runtime probes with exact signature capture (re-run at the Finding 6 clarification baseline: disposable /tmp database, `prisma`/`@prisma/client` 6.19.2 resolution of the `^6.11.1` pins — NOT application code, no workspace artifact touched; the correction-baseline probe record contained no exact signatures, so the probes were re-run to capture them):** with `isolationLevel: Serializable` explicitly requested, 15 contention rounds (8 × 2-way, 4 × 4-way, 3 × 6-way concurrent grant races on one `(org, user, scope)` key) each ended with EXACTLY ONE GRANTED row — zero partial rows, no double commit, no §2.3-invariant violation in any round; 2-way rounds produced ZERO failures (one `created: true`, one truthful `created: false`); failed attempts were proven atomic by per-round row counts and a zero-row slow-transaction probe. All 27 observed contention failures (4-way/6-way rounds) surfaced as `P1008` ×20 or `P2028` ×7 — **`P2034` was NEVER observed on SQLite**. The EXACT recorded signatures: `P1008` — one variant, message "Socket timeout (the database failed to respond to a query within the configured timeout).", `meta: { extra_hint: "" }`; `P2028` — three variants, all with the underlying error in `meta.error`: (a) "Transaction already closed: A query cannot be executed on an expired transaction. The timeout for this transaction was {timeout} ms, however {elapsed} ms passed since the start of the transaction. Consider increasing the interactive transaction timeout or doing less work in the transaction." (sometimes with `meta.modelName` set), (b) the same with "A commit cannot be executed on an expired transaction.", (c) "Transaction not found. Transaction ID is invalid, refers to an old closed transaction Prisma doesn't have information about anymore, or was obtained before disconnecting.". **DECISIVE distinguishability finding (the basis for rule 3's PENDING classification):** a single NON-contention transaction (deliberately slow callback, `timeout: 100`, zero concurrent writers) failed with `P2028` carrying the SAME "Transaction already closed … expired transaction" signature as the contention failures (differing only in the elapsed/timeout numbers) — so that signature does NOT reliably indicate contention; the `P1008` "Socket timeout" variant is likewise a generic stall surface (any query stall can produce it; the reference gives `P1008` no contention-specific semantics). The evidence therefore CANNOT safely distinguish SQLite contention from other `P1008`/`P2028` failures. The correction-baseline probe record (concurrent revocation races ended with zero current GRANTED rows; mixed grant/revoke batches deterministic) is unaffected by this re-run. (These probes verify mechanism, signatures, and rollback behavior only; they are NOT the §6 item 10 concurrency suite, which is implementation-time work.)
- **PostgreSQL runtime verification: NOT performed — unavailable.** No disposable PostgreSQL instance exists in the planning environment (no `psql`/`postgres` binary, no Docker, no managed instance). The PostgreSQL facts above are documentation- and type-level evidence only. PostgreSQL runtime verification of the corrected contract is explicitly PENDING (§6 item 10, §10); cross-provider verification is NOT claimed.
- SQLite has a single-writer architecture: concurrent write transactions do NOT interleave — a conflicting writer either waits (serializing) or fails with an atomic timeout, never partially applying. Prisma offers NO row-level locking on SQLite (no `SELECT ... FOR UPDATE`); any contract relying on row locks would be an invented capability and is therefore not used.
- **Repository retry/transaction patterns (re-verified at the clarification baseline):** the house bounded-retry precedent (`src/lib/laxii/retry.ts`) is a strict allowlist classifier — a fixed `RETRIABLE` set, bounded attempts, deterministic backoff, and fail-fast on timeouts and unknown errors ("a retry may never turn a real failure into a fake success"); the consent house pattern (`src/lib/ox/consent.ts` L138/L212) runs read-decide-write-audit inside one interactive transaction. The §A.3 classifier follows both precedents.
- The finding is accurate: read-then-create (grant) and current-row-update (revoke) inside a transaction prevent lost updates ONLY when conflicting transactions cannot interleave between the read and the write — which is exactly what READ COMMITTED does NOT guarantee on PostgreSQL (the retracted claim) and what `Serializable` DOES guarantee on both providers. No schema-level uniqueness constraint on the proposed `WorkforceAnalyticsConsent` model prevents two simultaneously-current GRANTED rows today (§A.3 fallback below).

**Concurrency contract (for the NEW workforce service `src/lib/wf/` — consent lifecycle AND manager-targeted consent-gated writes; the existing candidate `ox/consent.ts` behavior is unchanged).**

1. **Serializable isolation, explicitly requested**: every consent-lifecycle transaction AND every manager-targeted consent-gated write transaction (§A.2 — the consent read, authorization, workforce-record write, and strict audit of that path) passes `isolationLevel: Prisma.TransactionIsolationLevel.Serializable` in the interactive-transaction options — on BOTH SQLite and PostgreSQL (verified requestable for pinned Prisma 6.19.2 on both providers: version-pinned docs table + per-provider generated client surface). Explicit `maxWait` and `timeout` values are set (not the silent defaults) so contention behavior is deterministic and testable.
2. **One transaction, whole decision**: the ENTIRE consent decision and write — the fresh current-consent read, the authorization data still needed, the write, and the strict audit record (§A.1) — stays inside the SAME interactive transaction. No decision is made outside the transaction and no state is read outside it. This applies identically to the manager-targeted path (§A.2 four-step requirement): the subject's consent read, the authorization decision, the workforce-record write, and the strict audit event are ONE Serializable transaction (Finding 6: the Serializable requirement is NOT limited to `grantWorkforceConsent`/`revokeWorkforceConsent`).
3. **Strict retry classifier — retry ONLY the documented transaction-conflict error; the retryable set is a fixed, documented constant (Finding 6 correction)**: `P2034` — the pinned-version write-conflict/deadlock error ("Transaction failed due to a write conflict or a deadlock. Please retry your transaction"), the ONLY error the version-pinned v6 documentation gives retry guidance for, and the expected PostgreSQL serialization-failure surface (runtime confirmation pending §6 item 10). **`P1008` and `P2028` are NOT retryable by error code alone** — they are broad categories ("Operations timed out after `{time}`" / "Transaction API error: `{error}`"), and the recorded planning-time probes PROVED their observed SQLite signatures are not contention-specific (the identical `P2028` "Transaction already closed … expired transaction" signature arises from a plain slow transaction with zero contention; the `P1008` "Socket timeout" variant is a generic stall surface — exact signatures recorded above). On SQLite, `P1008`/`P2028` may be retried ONLY IF a contention-specific signature is verified — exact message, metadata, and/or nested cause — AND the transaction is proven to have rolled back, AND differential probes prove that signature cannot arise without contention. **With the recorded evidence that condition is NOT met: the SQLite `P1008`/`P2028` contention mappings are marked PENDING (not verified as contention-specific) and the classifier MUST treat `P1008`/`P2028` as non-retryable — fail closed — until and unless implementation-time verification records such a signature (if none can be established, they remain permanently non-retryable).** Generic transaction timeouts, transaction-API failures, connection-pool acquisition failures (`P2024`), validation failures, constraint violations, authorization refusals, and every unknown error fail immediately and explicitly — never retried. (Retrying a `P2034` conflict whose commit outcome is uncertain is safe ONLY because the contract requires a verified idempotency mechanism that also covers audit effects, verified at implementation time by §6 item 10: rule 4 re-runs the whole callback with a fresh read; an attempt that actually committed resolves on re-read to the truthful already-applied result (`created: false` for a grant; the existing declaration row for a manager/self declaration — the §4 `@@unique` constraints on `EmployeeSkill`/`EmployeeRoleCoverage` make a duplicate declaration impossible at the database level) WITHOUT appending a duplicate audit row — the audit event accompanies only the actual state transition. No retry safety is claimed for any operation lacking that verified mechanism.)
4. **Retry re-runs the ENTIRE transaction callback in a NEW transaction** — including the fresh current-consent read and the audit write — never just the write; for the manager-targeted path the re-run covers the full §A.2 four-step sequence (consent re-read → authorization → workforce write → strict audit). Bounded to **three attempts** with a deterministic short backoff; three is retained because the pinned-version evidence gives no basis for a different bound (the planning-time probes never needed more than one retry to converge, and the pinned docs prescribe no specific retry count — their conflict-handling example is a bounded retry loop).
5. **No false success**: on retry exhaustion the operation fails with an explicit error; nothing is reported as granted or revoked. Transactions are atomic — a conflicted or timed-out attempt leaves no partial rows and no audit rows for the failed attempt (empirically confirmed in the SQLite probes: per-round row counts and a zero-row slow-transaction probe).
6. **Truthful idempotency and default-deny preserved**: an idempotent re-grant against a current grant still returns `created: false`; a revoke of nothing still returns its truthful reason; any operation that did not commit is never reported as applied.
7. **Deterministic resolution preserved**: current consent = latest row per `(organizationId, userId, scope)` by `createdAt DESC, id DESC` (§2.3), unchanged by concurrency handling.
8. **Documented fallback — flagged NOT ready-to-implement (Finding 6 recheck)**: the previously recorded fallback — a database-enforced partial unique index on `(organizationId, userId, scope)` restricted to `status = 'GRANTED'` — was rechecked against the append-lifecycle and expiry semantics and is NOT ready-to-implement as stated: expiry is a resolution-time concept (§2.3) that never updates the row in place, so an EXPIRED grant row KEEPS `status = 'GRANTED'` with `expiresAt` in the past (§4: `expiresAt DateTime?`; only revocation flips status). A status-only partial unique index would therefore treat that expired row as a current grant and BLOCK the legitimate subsequent re-grant — a false conflict that breaks the §2.3 lifecycle. No predicate form has been verified to distinguish a current from an expired GRANTED row within a partial index, and no such design is proposed or authorized here. The fallback is therefore NOT presented as a ready coordination alternative: any database-enforced uniqueness strategy requires a separately owner-authorized design + migration decision that first PROVES predicate and lifecycle compatibility with append-history AND expiry. It remains NOT adopted in the v1 design (the Prisma schema language has no partial-index syntax and it would require raw migration SQL outside the additive no-migration planning boundary). No invented row locks, advisory locks, or Prisma capabilities are relied on anywhere in this contract.

**Outcome matrix (guarantees under the corrected contract).**

| Concurrency | Guaranteed outcome |
|---|---|
| grant ∥ grant | Exactly ONE appended GRANTED row; the other attempt either re-reads the committed grant and returns the existing row (`created: false`) or fails atomically — retried ONLY when the failure classifies as the verified conflict error `P2034` (rule 3), to the same truthful outcome; every other failure class fails closed without retry. Two simultaneously-current GRANTED rows can never coexist. |
| grant ∥ grant after a prior revocation | Same as above on the fresh ledger state — the prior REVOKED row is never resurrected; the winner appends a NEW row. |
| revoke ∥ revoke | One flips the current row to REVOKED; the other re-reads and returns a truthful no-op (`revoked: false`, reason REVOKED) or fails atomically — retried only when the failure classifies as `P2034` (rule 3); other failures fail closed. Final state unambiguous. |
| grant ∥ revoke | Serializable total order: revoke-then-grant (fresh GRANTED row) or grant-sees-current-then-revoke-flips (REVOKED). The final state is a deterministic function of the serialization order; both orders are default-deny safe. |
| manager-targeted declaration ∥ subject revokes consent | The §A.2 four-step path re-checks the subject's CURRENT consent inside the SAME Serializable transaction as the declaration write and its strict audit: either the declaration serializes FIRST, while consent is current, and commits atomically with its audit record; or the revocation serializes FIRST, consent is no longer current, the declaration fails its in-transaction consent check, and any whole-transaction retry (rule 4) re-reads consent fresh and REFUSES the declaration again (uniform 404 per §A.2 step 7). A declaration can never commit against consent that is no longer current, and no partial declaration row or orphan audit event can survive a lost race. |
| conflict/timeout failure | Atomic rollback, zero rows written, zero audit rows for the failed attempt; retried ONLY when the failure classifies as the verified conflict error `P2034` (rule 3) — all other failures, including every `P1008`/`P2028` under the PENDING SQLite mappings, fail closed without retry. |
| retry exhaustion | Explicit failure, transaction rolled back, zero rows written, zero audit rows, no success reported. |

**Tests specified for implementation time** (§6 item 10 — the full eight-scenario, two-provider contract): (i) two grants from no consent row; (ii) two grants after a prior revocation; (iii) two simultaneous revocations; (iv) grant racing revoke; (v) manager-targeted employee declaration racing the subject's consent revocation; (vi) serialization/write-conflict retry succeeding truthfully; (vii) retry exhaustion failing explicitly with zero rows written; (viii) final ledger state and `getCurrentWorkforceConsent` agreement (no simultaneously-current duplicates; default-deny safe). The suite runs separately against the QA SQLite environment AND a disposable PostgreSQL database using the actual PostgreSQL deployment schema; SQLite results are never substituted for PostgreSQL verification, and PostgreSQL runtime verification remains explicitly PENDING (§10) until such an environment exists. The suite also carries the mandatory retry-classification sub-suite of §6 item 10: verified-conflict (`P2034`) retry; conditional retry of a provably contention-specific SQLite signature (PENDING with the recorded evidence — rule 3); unrelated `P1008` NOT retried; unrelated `P2028` NOT retried; unknown errors fail immediately; every failed attempt leaves zero operation rows AND zero audit rows; retry exhaustion fails truthfully. Classifier cases are exercised with injected error instances carrying the exact signatures recorded above (no invented signatures) plus real races where observable.

### A.4 Finding 4 — Retention and cascading deletion (explicit, not silent)

**Verified ground truth.** The proposed §4 schema cascades `WorkforceAnalyticsConsent` / `EmployeeSkill` / `EmployeeRoleCoverage` rows on BOTH parent deletions (`onDelete: Cascade` to `User` and `EmployerOrganization`), matching the existing house pattern (`CandidateVisibilityConsent` likewise cascades on user deletion; `EmployerOrganization` cascades its child resources). `AuditEvent.actorUserId` is `onDelete: SetNull` (verified `prisma/schema.prisma` L1411–1413) and `AuditEvent` rows are otherwise FK-free, so audit events survive parent deletion.

**The plan therefore explicitly does NOT claim that append-lifecycle history is permanently retained: consent and declaration history persists only while the parent user and organization rows exist.** The §4 model comments now state this.

**Retention behavior per lifecycle event.**

| Event | Workforce consent rows | EmployeeSkill / EmployeeRoleCoverage rows | AuditEvent rows |
|---|---|---|---|
| Membership removal (`EmployerMembership.status → REMOVED`) | RETAINED — no FK to membership; rows remain but resolve to NO consent (enforcement requires ACTIVE membership) and are invisible on every workforce surface | RETAINED — likewise gated from every workforce surface by the ACTIVE-membership requirement | RETAINED |
| Consent revocation → re-grant | RETAINED (append-lifecycle: revoked row updated in place, re-grant appends a new row) — full ledger history while parents exist | n/a | RETAINED |
| User / account deletion | DELETED (cascade via user FK) — data minimization on subject deletion, consistent with the existing candidate-consent house pattern | DELETED (cascade via user FK) | RETAINED — actor FK nulled (`SetNull`); `meta`/`targetId` are plain strings and are NOT scrubbed by any current mechanism |
| Employer organization deletion | DELETED (cascade via organization FK) — tenant data minimization, consistent with the org-cascades-children house pattern | DELETED (cascade via organization FK) | RETAINED — the organization survives only as a string in `meta` |

**OPEN retention decisions (owner; NOT resolved by this amendment; NO legal retention period is invented or proposed).**

- **R1 — audit `meta` scrubbing after parent deletion**: the platform has no meta-scrubbing subsystem today; retaining meta identifiers after user/org deletion is the current house behavior. Whether workforce audit meta (which records `organizationId` / `subjectUserId` / `actorUserId` as strings) must be scrubbed on parent deletion is a privacy-policy owner decision.
- **R2 — `AuditEvent` retention period**: none is defined anywhere in this plan and the platform has no purge job; any retention period is an owner/legal decision, out of scope here.
- **R3 — organization-deletion alternative**: RESTRICTing organization deletion while workforce consent history exists (archive-first) is technically possible but is NOT recommended (it diverges from the house cascade pattern and complicates tenant offboarding). Recorded for completeness; the owner confirms cascade as the default.
