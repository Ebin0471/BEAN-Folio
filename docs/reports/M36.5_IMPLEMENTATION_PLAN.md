## 2. OD-2 — Workforce-analytics consent layer (design)

### 2.1 Storage decision: a NEW dedicated ledger, not a new scope on the candidate table

The plan proposes a new `WorkforceAnalyticsConsent` model rather than adding a scope value to `CandidateVisibilityConsent`. Rationale:

1. The approved design states workforce-analytics consent **must be separate** from candidate DISCOVERY consent, and architecture §16.2 specifies "New consent scope/ledger for employees (distinct from `CandidateVisibilityConsent`) ... No reuse of DISCOVERY."
2. **Keying**: employment is organization-scoped; the same user may be a member of several organizations with different consent states. Workforce consent is therefore per `(organizationId, userId)`. `CandidateVisibilityConsent` is keyed by `userId` alone with no `organizationId` column — reuse would require modifying the existing candidate consent model (a non-additive change to a production consent ledger) or overloading candidate semantics.
3. **Vocabulary isolation**: a separate server-owned `WF_CONSENT_VERSION` means candidate consent-version pinning (`OX_CONSENT_VERSION`) and workforce pinning never interact; candidate consent state can never satisfy a workforce check and vice versa.
4. **Semantic hygiene**: "must not treat organizational membership as employee consent" — a dedicated table makes the distinction auditable and unambiguous at the schema level.

### 2.2 Vocabulary (new constants, proposed `src/lib/wf/consent.ts` + `src/lib/wf/validation.ts`)

- `WF_CONSENT_SCOPES = ["WORKFORCE_ANALYTICS"]` — the single approved purpose. Future workforce purposes append here; candidate scopes are never valid in the workforce ledger.
- `WF_CONSENT_STATUSES = ["GRANTED", "REVOKED"]`; `WF_CONSENT_SOURCES = ["WORKFORCE_SELF_SERVICE"]`; `WF_CONSENT_VERSION = "M36.5-WF-CONSENT-V1"` (server-owned; never accepted from the client — strict zod input schemas only).

### 2.3 Lifecycle (mirrors the candidate ledger invariants)

- **Append-lifecycle history**: one row per grant; revocation updates the current row in place (`status REVOKED` + `revokedAt`); a re-grant creates a NEW row; no prior consent state is ever overwritten.
- **Current consent** = latest row per `(organizationId, userId, scope)` (deterministic `createdAt DESC, id DESC`), valid only while `status` is GRANTED and (`expiresAt` is null or in the future). NO_ROW / REVOKED / EXPIRED / wrong scope all resolve to **NO consent** — explicit default-deny (OD-2 rule 3).
- **Member self-service only**: grant and revoke require `actorUserId === subjectUserId` with the identity taken from the session, never from client input. OWNER/ADMIN (and every other actor) is refused — the approved design grants nobody the right to consent on behalf of an employee.
- **Membership is not consent**: grant/revoke require an ACTIVE `EmployerMembership` in that organization at call time (via the existing `getMembership` check). REMOVED members' historical rows are retained for audit but resolve to NO consent for analytics (enforcement requires ACTIVE membership AND current consent).
- **Truthful operations**: idempotent re-grant against a current grant (`created: false`); revoking when nothing is revocable returns a truthful reason (no fabricated success).
- **Revocation respected by subsequent access** (OD-2 rule 7): every analytics read re-checks consent fresh from the ledger per request — nothing cached, no event-sourced replay, exactly the `specialist-tools` / `portfolio-tools` enforcement pattern.

### 2.4 Access rules (the documented OWNER/ADMIN authorization required by OD-2 rule 5)

| Actor | Own declared workforce info | Another member's info (analytics roster) | Consent ledger |
|---|---|---|---|
| Employee (any role, ACTIVE membership) | Self-inspection always allowed (OD-2 rule 4) — own data; consent governs analytics USE, not self-view | Never | Own ledger: inspect / grant / revoke (self-service) |
| OWNER / ADMIN | Own data as above | **Only while that member has CURRENT `WORKFORCE_ANALYTICS` consent**; members without consent are EXCLUDED from results (per-member exclusion, mirroring the candidate discovery consent gate — not a hard error for the whole query); fresh read per request; every access audited | Read-only for audit purposes; may NOT grant/revoke on behalf of anyone |
| RECRUITER / HIRING_MANAGER / VIEWER | Own data as above | Never | Own ledger only |
| Any actor, foreign organization | Never (404 existence-hiding deny) | Never | Never |

Additional binding rules:

- OWNER/ADMIN roster access additionally passes the existing organization gates (`requireOrgRole(orgId, actor, OX_MANAGER_ROLES)`; org verification gates unchanged where they apply).
- Every OWNER/ADMIN analytics access emits an audit event recording actor, organization, the consented members included, and result count (OD-2 rule 6).
- **No cross-organization benchmarking, ever**: every query is bound to one `organizationId` derived from the caller's verified membership; no aggregate or comparative endpoint exists in this design.

### 2.5 Enforcement point

Enforcement lives in a new service layer (`src/lib/wf/`), NOT re-implemented in routes — mirroring the `ox/consent.ts` invariant header ("routes must NOT re-implement them"). Routes only authenticate (`getSessionUser`), take `organizationId` from the URL path, and delegate. If a future RIISHE tool ever consumes workforce data, the tool-boundary rule applies unchanged (`ctx.userId` re-verification + `requireOrgRole`).

### 2.6 Audit actions (new constants appended to the existing registries in `src/lib/ox/audit.ts`)

- `wf.consent.granted`, `wf.consent.revoked` (target `WORKFORCE_ANALYTICS_CONSENT`)
- `wf.workforce.info.viewed` (OWNER/ADMIN analytics access; meta: organizationId, member ids included, resultCount)
- `wf.skill.declared`, `wf.skill.updated`, `wf.skill.removed` (target `EMPLOYEE_SKILL`)
- `wf.role_coverage.declared`, `wf.role_coverage.updated`, `wf.role_coverage.removed` (target `EMPLOYEE_ROLE_COVERAGE`)

All events go through `auditOX` (the one audit store, `AuditEvent`); meta always records `organizationId`, `subjectUserId`, `actorUserId`, and the skill/role identifier where relevant.

## 3. OD-4 — Additive storage layer (design)

### 3.1 Models

Two new additive models, both keyed `(organizationId, userId)` per the approved minimum design (§16.2 OD-4):

- **`EmployeeSkill`** — employee-declared skills. `skillId` references the EXISTING `Skill` taxonomy (L235). Resolution matches EXISTING `Skill` rows by slug or exact label via a new `resolveEmployeeSkillIds` mirroring `resolveOpportunitySkillIds` — never upserted, never a competing taxonomy. Unique `(organizationId, userId, skillId)`.
- **`EmployeeRoleCoverage`** — role-coverage declarations. `roleKey` references the EXISTING code-level profession taxonomy (`src/lib/professions/taxonomy.ts` slugs), validated at write time against `flattenTaxonomy()`; never free-form, never a new taxonomy. Unique `(organizationId, userId, roleKey)`.

Both carry `source` (`SELF_DECLARED | OWNER_ADMIN_DECLARED`) and `declaredByUserId` (loose ref, house style) as **provenance only — never verification**. Removal is a hard delete of the declaration row plus an audit event (declarations are self-service data; the audit ledger preserves the history).

### 3.2 Write authorization matrix (OD-4 rules 4–5 via OD-2)

| Operation | Authorization |
|---|---|
| Employee declares/updates/removes OWN rows | ACTIVE `EmployerMembership` in that org (any role); allowed regardless of own consent state (own data, self-service); audited |
| OWNER/ADMIN declares/updates a MEMBER's rows | `requireOrgRole(orgId, actor, OX_MANAGER_ROLES)` **AND** the subject member's CURRENT `WORKFORCE_ANALYTICS` consent (strict reading: OD-4 rule 5 routes modification authorization through the OD-2 rules; modification of an employee's workforce data is an access to employee information for workforce purposes). Refused otherwise with a generic refusal (no existence leak). Audited with actor + subject |
| OWNER/ADMIN removes a MEMBER's rows | Not provided in v1 (declarations belong to their subject; removal is self-service). Documented as a deliberate limitation |
| RECRUITER / HIRING_MANAGER / VIEWER writes | Never |
| INVITED / SUSPENDED / REMOVED members | Automatically excluded by `requireOrgRole` / `getMembership` status semantics |
| Cross-organization writes | Never — 404 existence-hiding deny |

### 3.3 Consent-aware access and retrieval

- **Self read**: an ACTIVE member always sees their own rows and own consent ledger for that org (OD-2 rule 4).
- **OWNER/ADMIN analytics roster**: single-org read; per-member fresh consent gate with exclusion semantics (§2.4); audited per access.
- **No other read path exists**: no endpoint, service function, or query in this design exposes one member's workforce records to another member, to recruiters, or across organizations.

### 3.4 No automatic VERIFIED evidence (OD-4 rule 6)

- No code path in this milestone creates or updates `TrustVerification` rows, touches `EVIDENCE_LEVELS`, or upgrades any evidence level. Declared data is `SELF_DECLARED` provenance and nothing else.
- A dedicated regression test asserts zero `TrustVerification` writes and unchanged evidence-ladder output after declaration operations (§6).

### 3.5 Preserved semantics

- Candidate portfolio and evidence semantics untouched; `CandidateOpportunityProfile` is never treated as an employee record; candidate consent surfaces (`CandidateVisibilityConsent`, the O2 routes) keep their exact behavior — the workforce layer never reads them and they never read the workforce layer.
- No weakening of any existing membership or tenant-isolation check: `requireOrgRole`, `getMembership`, `orgIsVerified`, `countActiveOwners`, and the 404-deny convention are consumed as-is, never modified.

## 4. Exact proposed Prisma schema (ADDITIVE — NOT applied)

Application requires separate owner authorization (decision record §6). During implementation, the schema would be applied ONLY via `prisma db push` inside an isolated QA worktree with a pinned `DATABASE_URL` and the `scripts/ops/qa-db-env.sh assert --must-exist` guard — never in the legacy workspace, never against any production database. No migration files, no backfill.

```prisma
/// M36.5 OD-2 — Workforce-analytics consent ledger (employee consent; distinct
/// from CandidateVisibilityConsent by approved design: separate table, separate
/// vocabulary, per-(organizationId, userId) keying). Append-lifecycle history:
/// one row per grant; revocation updates that row in place (status REVOKED +
/// revokedAt) and a re-grant creates a NEW row — no prior state is overwritten.
/// Current consent = the latest row per (organizationId, userId, scope); valid
/// only while status GRANTED and (expiresAt is null or in the future). No row
/// at all also means no consent. Organizational membership is NOT consent.
model WorkforceAnalyticsConsent {
  id             String    @id @default(cuid())
  organizationId String
  userId         String
  user           User      @relation("workforceConsents", fields: [userId], references: [id], onDelete: Cascade)
  organization   EmployerOrganization @relation("orgWorkforceConsents", fields: [organizationId], references: [id], onDelete: Cascade)
  scope          String // WORKFORCE_ANALYTICS — workforce purposes only; candidate scopes are never valid here
  status         String // GRANTED | REVOKED — one row per grant lifecycle
  consentVersion String // server-owned (WF_CONSENT_VERSION) recorded at grant time
  source         String // server-owned provenance (WORKFORCE_SELF_SERVICE) — never accepted from the client
  grantedAt      DateTime  @default(now())
  revokedAt      DateTime?
  expiresAt      DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([organizationId, userId, scope, createdAt]) // current-consent lookup: latest row per (org, user, scope)
  @@index([organizationId, userId, status])
}

/// M36.5 OD-4 — Additive employee-declared skill record, keyed by
/// (organizationId, userId) per the approved minimum design. skillId references
/// the EXISTING Skill taxonomy — resolution matches existing rows only (never
/// upserted, no competing taxonomy). SELF-DECLARED data only: these rows are
/// never evidence — no code path may create or modify TrustVerification rows or
/// upgrade any evidence level because of them.
model EmployeeSkill {
  id               String   @id @default(cuid())
  organizationId   String
  userId           String
  user             User     @relation("employeeSkills", fields: [userId], references: [id], onDelete: Cascade)
  organization     EmployerOrganization @relation("orgEmployeeSkills", fields: [organizationId], references: [id], onDelete: Cascade)
  skillId          String
  skill            Skill    @relation(fields: [skillId], references: [id], onDelete: Cascade)
  source           String   @default("SELF_DECLARED") // SELF_DECLARED | OWNER_ADMIN_DECLARED — provenance only, never verification
  declaredByUserId String // actor of the declaration (loose ref — house style)
  note             String?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([organizationId, userId, skillId])
  @@index([organizationId, userId])
  @@index([skillId])
}

/// M36.5 OD-4 — Additive employee role-coverage record, keyed by
/// (organizationId, userId). roleKey references the EXISTING code-level
/// profession taxonomy (src/lib/professions/taxonomy.ts slugs) — validated at
/// write time against the published vocabulary, never free-form, never a new
/// taxonomy. SELF-DECLARED data only (see EmployeeSkill).
model EmployeeRoleCoverage {
  id               String   @id @default(cuid())
  organizationId   String
  userId           String
  user             User     @relation("employeeRoleCoverage", fields: [userId], references: [id], onDelete: Cascade)
  organization     EmployerOrganization @relation("orgEmployeeRoleCoverage", fields: [organizationId], references: [id], onDelete: Cascade)
  roleKey          String // existing profession-taxonomy slug — validated, never free-form
  source           String   @default("SELF_DECLARED") // SELF_DECLARED | OWNER_ADMIN_DECLARED
  declaredByUserId String
  note             String?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@unique([organizationId, userId, roleKey])
  @@index([organizationId, userId])
  @@index([roleKey])
}
```

**Additive relation arrays on existing model blocks (the ONLY edits to existing models — no column, type, or constraint changes):**

- `User`: `workforceConsents WorkforceAnalyticsConsent[] @relation("workforceConsents")`, `employeeSkills EmployeeSkill[] @relation("employeeSkills")`, `employeeRoleCoverage EmployeeRoleCoverage[] @relation("employeeRoleCoverage")`
- `Skill`: `employeeSkills EmployeeSkill[]`
- `EmployerOrganization`: `orgWorkforceConsents WorkforceAnalyticsConsent[] @relation("orgWorkforceConsents")`, `orgEmployeeSkills EmployeeSkill[] @relation("orgEmployeeSkills")`, `orgEmployeeRoleCoverage EmployeeRoleCoverage[] @relation("orgEmployeeRoleCoverage")`

## 6. Verification plan (maps decision record §5, bullet for bullet)

New suites (per-file execution via `scripts/ci/run-tests.sh` against the isolated QA `custom.db`; `randomUUID` fixtures; cookie-jar session pattern per `tests/ox-candidate-profile-consent.test.ts`):

1. **Consent-denied behavior** — `tests/wf-consent.test.ts`: no row / REVOKED / EXPIRED / wrong scope ⇒ member excluded from OWNER/ADMIN roster; OWNER/ADMIN modification of that member's rows refused; candidate DISCOVERY consent has zero effect on workforce checks (and vice versa).
2. **Grant and revocation behavior** — append lifecycle (re-grant creates a new row; idempotent re-grant; truthful revoke-of-nothing); server-owned version/source stamping; audit events (`wf.consent.granted` / `wf.consent.revoked`); **revocation respected by subsequent access** (roster excludes the member immediately, fresh read, nothing cached).
3. **Employee self-access** — self-inspection of own declared info and own ledger regardless of consent state; self grant/revoke; OWNER/ADMIN attempt to grant/revoke on behalf refused; non-member refused.
4. **Unauthorized OWNER/ADMIN access** — OWNER/ADMIN without the subject's consent sees the member excluded; RECRUITER/HIRING_MANAGER/VIEWER see no roster endpoint success; consent-less member data never returned.
5. **Cross-tenant isolation** — org A OWNER/ADMIN against org B: 404 existence-hiding deny; every workforce query org-bound; no cross-org aggregate endpoint exists (asserted by route inventory test).
6. **Skill declaration/update authorization** — self-service CRUD with ACTIVE membership; existing-rows-only skill resolution (unknown slug/label rejected, never upserted); `roleKey` validated against the profession taxonomy (unknown rejected); OWNER/ADMIN write with subject consent succeeds with `OWNER_ADMIN_DECLARED` provenance and audit; OWNER/ADMIN write without subject consent refused; suspended/removed member refused; non-manager role write to others refused.
7. **No automatic VERIFIED evidence** — after declaration operations: zero `TrustVerification` rows created/updated (DB assertion) and evidence-ladder output unchanged; `source` remains provenance-only.
8. **Existing regression suites preserved** — at minimum: `ox-discovery-consent`, `ox-candidate-profile-consent`, `ox-discovery-privacy`, `ox-tenant-isolation`, `ox-opportunity-authz`, `ox-opportunity-audit`, `ox-employer-org`, `workspace-context`, `riishe-m362-workforce-strategist`, `riishe-m364-candidate-relations`, `riishe-portfolio-evidence`, `universal-studio-capability-matrix` (registry counts unchanged: 18 specialists / 44 tools), `audit-regressions`.
